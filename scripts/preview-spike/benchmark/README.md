# Preview spike benchmark

This is a Development-only, operator-driven experiment. It does not deploy anything. The timed browser path exercises a hydrated fixture control and requires a real database response. Separate capability checks exercise CRUD on every fixture, two-user Native Auth on its fixture, and the application-mail fixture through its gateway and an independently read mailbox. These checks require the real, separately provisioned Development QA service integrations; the source and local tests alone do not establish hosted success. A timing target can be met while product acceptance remains `null` and `overallAcceptance` remains `incomplete`. `frameworkTargets: passed` applies only to the targets this harness defines; it cannot decide full G1 or G2, which also require the observations and customer paths in the [W41 specification](../../../docs/plan/specs/2026-11-14-live-project-previews.md).

Each fixture and instance gets a separate run. The runner records 20 or more wake and HMR attempts; each Next fixture also gets 20 or more cold-start attempts, each in a fresh session. It completes the Next cold sessions and confirms each deletion before creating the persistent session: the Development spike permits only one session at a time. Cold-start evidence checks that `node_modules` did not exist before install, that no backup was restored, which package-cache mode was used, and that the session was destroyed. `seeded` means public package archives were available in the image; `empty` starts with an empty package cache. Do not compare the modes as if they were identical.

Wake trials use the same persistent project and a verified backup. Before each timed trial, the measurement browser is closed and the authenticated control route explicitly stops the running container. The adapter requires both the stop response and a separate status read to report `lastStopReason: manual`, the same stopped generation and the same current backup. The journal records `sleepInduction: manual` for the run and each wake sample. The timer starts at the next browser navigation. The Worker uses the same container destruction and restore/start path for manual and idle stops; this does not claim that each timed trial waited ten minutes. The separate open-tab preflight below observes the actual idle policy. A successful result requires the same URL, a new generation, a restored backup, the fixture page and valid container-start, restore and dev-server-start timings. The timer includes the fixture heading and controls, two animation frames, and a real hydrated database action and response. On Native Auth this action is the fixture's separate unauthenticated DB readiness check; the other six use their notes read control. TanStack's control invokes a server function rather than `/api/notes`; the probe observes its request and rendered result. Sequential wake trials share an image and checkpoint; they are repeated trials, not independent projects or independent environmental conditions.

The capability checks bracket the persistent wake and HMR cohort. The Next cold cohort happens first because only one session can hold the lease; every timed cold navigation still requires its own hydrated DB action. Every fixture performs browser-driven create, update, reload/read and delete/read before and after the persistent cohort. Native Auth signs up and verifies two distinct synthetic users from actual inbox contents, logs in through separate browser contexts, checks cross-user isolation, retains both sessions through sleep and source edits, and checks logout and cookie replay. Mail sends the same unique ID exactly twice through the fixture, requires matching accepted receipts and reads one matching delivered message before and after the cohort. No second email journey is sent after timing. Auth user accounts remain in the authorized isolated QA realm; the fixture has no user-deletion control.

An additional preflight leaves a tab with a recognized HMR connection open through the idle interval. It checks that the container sleeps, stays asleep during the configured passive observation window, wakes on a trusted browser action, and supports HMR afterward. Only an idle policy configured to exactly 600,000 ms can meet the ten-minute policy target (`idlePolicyTargetMet`); shorter or longer intervals are characterization only. The adapter restores the edited file and takes a fresh backup before wake trials.

The adapter separately measures the Worker's confirmed stop observation (`stoppedAt`) relative to the unchanged `lastUserActivityAt`, reported as `idleSleepAfterMs` and `idleStopDelayMs`. Neither client waiting time, status polling nor provenance-readback duration substitutes for a stop timestamp. Missing stop evidence leaves timing unqualified. A stop before the configured ten-minute deadline has `idleTimingQualification: invalid-stop-before-policy-deadline` and fails the framework evidence check; it cannot establish ten minutes of inactivity. A stop observed at the deadline qualifies. A positive observed delay has `idleTimingQualification: incomplete-no-agreed-jitter-tolerance` and keeps the framework result incomplete; no jitter tolerance has been agreed (`idleJitterToleranceMs: null`), so this does not establish a provider failure. The one-second readback grace cannot turn such a delay into a timing pass. The passive window is reported separately and establishes only that bounded observation, not a continuous or unlimited no-wake guarantee.

HMR targets use `editToPaintMs`: file-write request dispatch to the visible unique marker followed by two animation frames. A private synchronous callback timestamps dispatch immediately before the edit POST's `fetch`, after its mandatory provider preguard and synced mutation intent. An independent browser observer captures paint completion while the control response, postguard and receipt validation are still pending. Both timestamps use the same Node `performance.now()` clock; browser and host clocks are never subtracted. The endpoint is the host's observation of completed animation frames, so browser-automation delivery overhead is conservatively included. No guessed overhead is subtracted.

The full guarded edit operation is retained separately as `operatorElapsedMs`, including before/after status reads, route guards and durable confirmations. It does not feed the HMR latency target. A sample needs one genuine dispatch callback, marker observation after that dispatch, completed paint and confirmed control/receipt checks. Missing, duplicate, reordered or invalid timing cannot yield a qualifying short number; a failed postguard still aborts the sample even if paint was already observed. The edit receipt's accepted-content SHA-256, generation and next source revision must match the request, the prior state and a fresh guarded status. That hash binds the accepted write, not an immutable guest filesystem after arbitrary guest execution. Cold and wake timing boundaries are unchanged.

HMR also requires the same document plus a recognized update for the edited module received after dispatch. The probe recognizes the [Vite `connected` and `update` protocol](https://github.com/vitejs/vite/blob/main/packages/vite/types/hmrPayload.d.ts), with a `js-update` whose `acceptedPath` matches that file. Ping, custom application messages, updates for another file, pre-dispatch frames and unknown payloads cannot set `hmrUpdateObserved`. A full reload message disqualifies HMR; a new document is recorded as `reload`.

For React/Vite, Vanilla/Vite and Astro, the archived fixture trees remain byte-identical. Before the first backup, the driver adds the same self-accepting client module to the disposable workspace and adds its script tag to the copied entry HTML or Astro page. Before each edit, the browser waits within the run deadline for that module's visible initial or previous marker; the Vite handshake alone does not show the module has loaded. The timed write changes only that already-loaded module's unique visible marker. The report identifies this as `instrumented-self-accepting-module`, includes the fixture-specific overlay descriptor hash, and leaves `nativeFixtureHmrAcceptance` null. This measures a real module update through the preview hostname; it does not establish React Fast Refresh, the original Vite entry edit, or Astro server-rendered page updates. A provider comparison must apply the same fixture-specific overlay bytes and measure the same workload on every provider. The separate original-entry reload observations below remain valid and are not reclassified as provider failures.

For the three Next fixtures, the disposable edit changes the `Id` label in the existing Client Component `src/app/notes.tsx`. This measures that Client Component update, not Server Component refresh. The Next 16.4.1 probe requires a same-origin `/_next/hmr` socket with a valid `turbopack-connected` handshake and a `turbopack-message` containing `partial` → `ChunkListUpdate` → `EcmascriptMergedUpdate`. The exact entry key must be `[project]/src/app/notes.tsx [app-client] (ecmascript)`, and its own `code` string must contain the current unique marker. A marker elsewhere in the frame or source map cannot establish the edit. The marker must also become visible in the same document; `reloadPage` disqualifies the result. Generic `built` or pathless `serverComponentChanges` messages, different project prefixes and unknown payloads fail closed. The parsed shapes were checked against the installed Next 16.4.1 sender, client and update types.

A separate local browser characterization on 15 November 2026 observed that exact entry and marker with Next 16.4.1, React 19.2.5 and a disposable fixture-root copy, with the document unchanged. The successful root-specific repetition used temporary polling (`watchOptions.pollIntervalMs: 100`); two attempts without polling observed no update within 20 seconds. This supports the narrow parser shape, not hosted reliability or latency, and changes no repository fixture or hosted watcher configuration. [Next's Fast Refresh documentation](https://nextjs.org/docs/architecture/fast-refresh) also describes cases that fall back to full reload; the document sentinel remains required. Fresh hosted measurements, the current fixture dependency versions and full G1/G2 acceptance remain unverified.

The empirical percentiles use the nearest-rank method: sort the successful durations and take rank `ceil(p × n)`. With 20 successful observations, p50 is rank 10 and p95 is rank 19. The report shows success-only percentiles as descriptive diagnostics. It never hides an error, timeout, reload, absent observation, incomplete journal, or missing provider evidence: any such failure makes the affected run fail its timing gate. HMR targets are p50 ≤1 s and p95 ≤3 s; Vite wake targets are p50 ≤5 s and p95 ≤10 s; Next wake targets are p50 ≤10 s and p95 ≤20 s; cold Next target is p95 ≤60 s. Astro and TanStack wake observations have no numeric target in this spike. These are not complete product acceptance results.

The schema 6 journal uses a new, exclusive `0600` file and contains fixed event names, timestamps, validated non-secret pins, numerical durations and boolean evidence. It adds the HMR workload and overlay identity to schema 5's capability events, explicitly recorded manual induction, timing boundary, dispatch/paint/control-confirmation evidence, and distinct `editToPaintMs`/`operatorElapsedMs` fields. For HMR, `elapsedMs` must equal the qualified `editToPaintMs`, and the outer operator duration must bound it; only that qualified duration feeds percentiles. Schema 5 and earlier cannot pass as equivalent evidence. It never stores control tokens, preview URLs, browser errors, mailbox contents or provider responses. A process interruption leaves the started sample visible; a torn last line is reported as an integrity failure while complete earlier lines remain readable. A separate exclusive `0600` file alongside the raw journal, with suffix `.resources.private.jsonl`, records lifecycle intents and outcomes, and the fixture-mail message ID and Auth account hashes before their operations, for reconciliation; it contains no control token and must remain private. The operator adapter must retain its own private mapping from its synthetic Auth accounts to those hashes. The raw measurement journal never contains session IDs, message IDs or capability URLs. A timeout, identity mismatch or uncertain provider error stops the run without retrying or deleting the possibly active session. Reconcile its state before starting a new run. If a create response was lost before its ID could be recorded, inspect the authenticated read-only `/__spike/lease` endpoint to identify the occupied slot. Do not create a replacement or issue a deletion until its actual state and ownership have been established. A successful run records deletion of its persistent session and backup; each cold session is separately deleted and confirmed.

The private resource journal also records a `runtime-checkpoint` for the verified setup, each cold session and each timed wake whose status has matching identity and valid phase and backup fields, including when the wake or capability proof fails. The status `previewId` must match that session's ID. The checkpoint alone does not assert a successful wake. It contains only the fixed fixture, instance and purpose; session ID, generation and source revision; backup UUID, SHA-256, source revision, generation and `backupCompressedBytes`; and the named controller UTC timestamps for container start, install and backup on cold/setup or restore on wake, and server start. The controller's `startedAt` is included when present. The other named phase timestamps, valid backup metadata and canonical UTC timestamps are required for future runs; malformed or missing values stop the attempt and leave its resources for reconciliation. The pinned Sandbox SDK 1.0.1 describes `DirectoryBackupRecord.size` as the R2-reported stored bytes of its `tar+zstd/1` object and checks it against the uploaded bytes; the checkpoint preserves that actual reported compressed size, not an estimate. It projects fields from setup/status responses already obtained, without another request, and never copies URLs, environment, QA data, credentials or a raw response. Cold projections remain in memory until the caller stops its timer, then are synced before deletion; wake projections are synced after the wake timer and proof. Invalid projections or an interrupted or uncertain checkpoint write fence further mutations for that adapter; the write is not retried and resources are not cleaned up automatically. This supplies raw supporting evidence for a future attempt; it does not establish hosted measurements or G1/G2 acceptance.

## Running after separate Development provisioning

Set the non-secret `PREVIEW_SPIKE_ROUTE_ID` from the verified deployment journal. Before and after every control-token-bearing request, the built-in adapter reads the fixed Cloudflare route and active Worker version and refuses drift. The QA mailbox adapter also requires `PREVIEW_SPIKE_WORKER_VERSION_ID` matching that same run. Its permit POST has a fixed 30-second deadline in addition to caller cancellation. These are sampled control-plane checks, not an atomic lock on a route change.

Read-only control status/lease and management GETs may make at most three attempts for HTTP429/5xx, a recognized transient network error or their own 15-second attempt timeout. Every attempt and backoff shares the original caller signal and absolute operation deadline; a caller timeout is never restarted. Retry-After is honored within that remaining budget. 401/403, malformed JSON/envelopes, identity/route/version drift and unknown transport errors fail closed. No control POST, DELETE or other mutation is retried, including a503 or lost response; its uncertain intent remains for reconciliation. Post-request target checks are still attempted on failed requests within the same budget. No timing threshold or measurement boundary changes.

Diagnostic waits use that same caller signal and absolute deadline. A rejected diagnostic fails closed with a fixed category; it is never retried. A pending write may finish later, but cannot delay cancellation or cause another request. The QA mail permit's precheck, POST and postcheck share one 60-second operation budget, tightened by a supplied absolute deadline and caller cancellation. Its POST retains its own 30-second maximum, and a failed POST still receives a bounded postcheck before returning an unknown outcome.

The private resource journal receives bounded `readonly-request` signals with fixed endpoint labels, pre/read/post/provenance phase, attempt number, numeric status, elapsed milliseconds and a fixed reason category. `control-target-check` distinguishes a failed read from a failed identity check. URLs, session paths, bearer values, bodies and raw exception text are never included. These signals establish only what a future attempt actually observes; an old redacted 15-second failure is compatible with a management timeout, not proof of one. Errors do not become empty lease/status or positive provenance evidence.

The following requires an already reviewed and available Development Worker, control secret, and browser driver. Never place the control token in a file tracked by Git or in command arguments. Select a local browser driver with an `openBrowser()` export returning a Playwright-compatible browser. Its path must be absolute. The mandatory built-in `provenance.mjs` verifier uses an existing `CLOUDFLARE_API_TOKEN` with read access to the Development Worker and Container application. It checks the sole active Worker version at 100%, its `SANDBOX` namespace, matching application and immutable version-bound `containers[].images.fixture` digest. SDK 1.x Durable Object-managed applications have no scheduled-application image or rollout to verify; see the [current application API](https://developers.cloudflare.com/api/resources/containers/subresources/applications/methods/get/). Unknown readback shapes fail closed. `SPIKE_CONTROL_TOKEN` remains in the process environment and the Worker secret store. No credential is written into either journal.

The Auth and Mail fixtures additionally require an absolute `PREVIEW_SPIKE_CAPABILITY_DRIVER` path to a reviewed local module exporting `createQaAdapter({ fixture })`. It returns a trusted operator adapter with:

- `auth({ sessionId, signal })` for Native Auth: returns `{ users: [{ email, password, name }, { email, password, name }], sender }`. The two addresses must be distinct, fresh synthetic accounts in the authorized isolated QA realm. This method only prepares and privately retains the account mapping; signup is performed by the browser.
- `mail({ sessionId, id, signal })` for Mail: returns `{ recipient, sender }` for the single explicitly authorized QA recipient and sender. It does not send or arm anything.
- `armMail({ sessionId, id, signal })` for Mail: calls the separately authorized, authenticated operator permit route for that exact session and unique message ID. It must not send the message itself.
- `readInbox({ kind, recipient, since, subject?, signal })` for both fixtures: waits for mailbox delivery and returns **all** matching actual inbox messages as an array of `{ id, to, from, subject, text, receivedAt }`; `receivedAt` is an ISO timestamp, `to` and `from` are normalized exact email addresses, and `text` is the delivered plain-text body. `kind` is `verification` or `mail`. For mail, search all messages with the exact unique subject since the supplied time, including duplicates; do not synthesize a message from a gateway receipt or return a success boolean. For Auth, return all fresh verification messages for the exact account. The harness validates sender, recipient, freshness, subject, body, the exact preview-origin verification link, and uniqueness. The mailbox read is sampled twice, not a guarantee about all future delivery. Respect the abort signal and never retry a mutation after an unknown outcome.

The supplied `../deployment/qa-adapter.mjs` implements this adapter and can also supply `openBrowser()`. Its mailbox transport requires a live trusted operator broker: set `SPIKE_QA_INBOX_QUEUE` to a new absolute pathname inside an owner-only directory, and keep a non-TTY stdin pipe open. The adapter appends bounded request metadata `{ version: 1, requestId, kind, recipient, since, subject? }` to an exclusive `0600` JSONL file. The broker searches and reads the real inbox, then sends exactly `{ requestId, messages: [{ id, to, from, subject, text, receivedAt }] }` as one JSON line to stdin; an empty array causes another request after five seconds. Mail bodies and tokens remain in memory and stdin, never in that queue or stdout. The adapter requires private `SPIKE_QA_MAIL_RECIPIENT`, `SPIKE_QA_MAIL_SENDER`, `SPIKE_QA_AUTH_SENDER`, `SPIKE_QA_AUTH_A_EMAIL`, `SPIKE_QA_AUTH_B_EMAIL`, `SPIKE_QA_AUTH_A_PASSWORD` and `SPIKE_QA_AUTH_B_PASSWORD` values as applicable. Auth addresses must be distinct plus aliases of the authorized recipient. The browser driver requires absolute `PREVIEW_SPIKE_PLAYWRIGHT_MODULE` and `PREVIEW_SPIKE_CHROME_BINARY` paths. The mailbox broker remains a trusted operator input; provider inbox authenticity and complete search depend on its real implementation and account access. The adapter does not create QA accounts, choose a recipient, obtain keys, authorize a sender or activate a provider integration. Missing broker or service wiring stops the run; local doubles cannot supply hosted evidence. Never put credentials, verification tokens, URLs or mailbox contents in source, console output, arguments or journals.

The local spike and fixture source must be committed, clean and at `sourceRevision`, and its lockfile must name the pinned Sandbox SDK. `fixtureSourceRevision` separately pins the Git archive consumed by `prepare-context.mjs`. The verifier recomputes the exact archive SHA-256 and source tree, compares them to the working fixtures and prepared context, and compares the context's container files to the clean source. Pins must match `worker/build-context/fixture-provenance.json`, generated from those archive bytes. `fixtureTreeSha256` is for the selected fixture; `fixtureArchiveSha256` covers the entire archived fixture set.

The historical spike benchmark uses its original pinned Git archive from the private operational record. A standalone public clone runs the provenance tests against its own committed fixture source. The tests prepare and verify that archive before checking that changed fixtures and tampered contexts are refused.

The deployed version message must start with `source <sourceRevision>;` (or `origin/main <sourceRevision>;`), its plain-text `SPIKE_SOURCE_REVISION` must match, and it must bind `CF_VERSION_METADATA`. Runtime status must report the pinned Worker version plus matching source revision, fixture revision, archive digest, selected fixture tree and overlay descriptor digest from the image metadata. `hmrOverlaySha256` must be the selected descriptor digest for the three instrumented fixtures and explicit `null` for the others; a missing or mismatched field refuses the run. Identity readbacks bracket setup, idle observation and every sample, outside the latency timers, with a final check after cleanup. Deployment identity must also remain stable across each provider readback. These are sampled checks, not continuous observation between them.

Reports call this `identityReadbackMatched` at evidence level `provider-readback-and-operator-source-claim`, with `cryptographicBuildAttestation: false`. Provider identity, image metadata and deployment annotations cannot cryptographically attest that the image or Worker was built from that source. The `PREVIEW_SPIKE_PROVENANCE_DRIVER` override is refused; an external always-true verifier cannot bypass the built-in checks. These source additions do not deploy or authorize a new deployment.

## Local framework characterization, 14 November 2026

On macOS with Node 24.6.0, pnpm 10.28.2, Vite 8.3.4, Astro 7.4.0 and headless Chrome driven by Playwright, one observed edit of each original React/Vite entry, Vanilla/Vite entry and Astro page resulted in a full document navigation. These are separate local framework observations, not Cloudflare failures or latency percentiles. Earlier attempts on React and Astro, and a later Vanilla attempt, timed out while the local watcher was not reliably observing writes; the observed React and Astro cases used polling. A disposable self-accept overlay also timed out in a repeat using fresh markers, so its earlier apparent React success was discarded. More controlled repetitions are required before attributing an HMR result to the provider or claiming a framework-wide property.

On 15 November a separate local-only test of the declared module overlay used explicit Vite watcher polling at 100 ms, a two-second watcher-settle period and atomic temporary-file renames. For each of the three fixtures four distinct edits produced the exact probe-module `js-update` and a visible marker in the same document, with no full-reload frame or navigation. An earlier run without explicit polling/settling timed out on all three. Neither observation establishes hosted watcher behavior, Cloudflare latency, React Fast Refresh or Astro page HMR.

To repeat, copy the three original fixture directories into a fresh temporary directory, install their lockfiles there with scripts disabled, and start their development servers bound only to loopback on ports 4171 (React/Vite), 4172 (Vanilla/Vite) and 4173 (Astro). For example, with `$SPIKE_TMP` set to a new temporary directory:

```sh
cp -R fixtures/cloudflare-preview/react-vite fixtures/cloudflare-preview/vanilla-vite fixtures/cloudflare-preview/astro-edge "$SPIKE_TMP/"
(cd "$SPIKE_TMP/react-vite" && pnpm install --frozen-lockfile --ignore-scripts --prefer-offline)
(cd "$SPIKE_TMP/vanilla-vite" && pnpm install --frozen-lockfile --ignore-scripts --prefer-offline)
(cd "$SPIKE_TMP/astro-edge" && npm ci --ignore-scripts --no-audit --no-fund --prefer-offline)
```

In separate terminals, run `CHOKIDAR_USEPOLLING=true CHOKIDAR_INTERVAL=100 pnpm exec vite --host 127.0.0.1 --port 4171 --strictPort` from the React copy, the same command with port 4172 from the Vanilla copy, and `CHOKIDAR_USEPOLLING=true CHOKIDAR_INTERVAL=100 npm exec -- astro dev --host 127.0.0.1 --port 4173` from the Astro copy. With absolute `PREVIEW_SPIKE_PLAYWRIGHT_MODULE` and `PREVIEW_SPIKE_CHROME_BINARY` paths set, run:

```sh
node scripts/preview-spike/benchmark/local-framework.mjs "$SPIKE_TMP"
```

The check refuses non-temporary directories or altered starting fixture files, waits for socket activity as a transport diagnostic, writes a unique marker in the disposable copy, records navigation/same-document evidence without recording socket URLs, and restores the file. Its `same_document` outcome is not protocol-validated HMR evidence, and `unobserved_or_timeout` is inconclusive. Stop the two Vite processes and run `npm exec -- astro dev stop` from the Astro copy afterward. Do not use this characterization as a hosted preview acceptance test.
