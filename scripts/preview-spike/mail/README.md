# Development QA mail integration

This G1-only integration serves the `next-app-mail` fixture and one explicitly authorized QA recipient in isolated Development. Local tests use synthetic services and addresses. Dated hosted observations and the currently active custody override are recorded in the [Mail repair checkpoint](../../../docs/plan/evidence/W41/20261116-live-preview-mail-repair-checkpoint.json); application-mail delivery remains open. This is not a production preview authority and does not establish G1 or G2 acceptance.

The isolated Development Worker `ohmyho-preview-spike-mail-development` has no public route or workers.dev URL. Its `QaMailPrivate` entrypoint binds the actual Development Core `DevAccessRuntime`, `GatewayCreditRuntime`, `MailSendRuntime` and existing `MailEgressEntrypoint`. It binds `QA_SPIKE_MAIL_AUTHORITY` to `ohmyho-preview-spike-development` / `SpikeMailAuthority`; that read-only method accepts `{ sessionId }` and returns `null` or exact `{ sessionId, generation, expiresAt }`. The spike authority must check the fixture, current running and ready state, unpoisoned generation and unexpired matching lease, without exposing its Durable Object namespaces or lifecycle operations. The private mail service rechecks the session and current Dev access, credit and exact mail-key scope before a gateway call. The gateway independently checks the project stamp, key, sender, billing and idempotency.

The mail and spike services reference each other. For a first deployment, `wrangler.bootstrap.jsonc` declares the same private Worker without the spike binding, so mail sends fail closed. After the spike Worker exists, deploy the reviewed final `wrangler.jsonc` and verify both bindings before running acceptance. The bootstrap and final profiles have the same account, Worker name, code, resources and services except for that one authority binding. These are the two-stage source profiles; the dated checkpoint records their actual Development deployment and subsequent binding override.

Provision `QA_MAIL_SCOPE` privately as an exact JSON object with `platform`, `fixture`, `organizationId`, `projectId`, `environmentId`, `handle`, `origin`, `principalId`, `devAccessEpoch` and `recipient`. The platform is `development`, the fixture is `next-app-mail`, and the recipient and tenant facts must be independently verified. `QA_MAIL_OPERATOR_TOKEN` must contain the same scoped high-entropy `SPIKE_CONTROL_TOKEN` used by the trusted control route. The source-candidate overlay binds `QA_MAIL_KEY_CUSTODY` to the existing Development runtime-secret-delivery Worker's `QaPreviewMailKey` entrypoint; the active hosted override is described below. Its zero-argument `read()` can only return the previously stored exact QA environment's mail key after current custody checks; it does not create or rotate a key. The relay reads it afresh inside each operation, rechecks it immediately before a send, and requires the real Core mail authority to authorize its digest for the configured scope. Neither key nor operator token is returned to the guest, browser, control status, or configuration. No static `QA_MAIL_KEY` secret or fallback is used.

`buildQaMailCustodyConfig(base)` produces a temporary overlay of the complete existing Development runtime-secret-delivery profile, adding only its Development QA enable flag and the fixed Core `QaPreviewMailKeyAuthority` binding. It preserves the existing services, encryption-secret declarations and schedule. Write it beside the canonical profile to preserve relative paths; restore and verify the canonical version before retiring QA resources, without removing credential material. That source-candidate overlay requires those entrypoints in both services. After a later shared Development release removed them, the hosted QA relay was bound to a dedicated fixed-scope broker instead. The broker holds a copy of the existing one-fixture Dev key, reads only its fixed metadata and current grant, credit and Mail/sender authority, and has no public fetch route. It does not carry the master cipher key. The newer shared Core and Runtime Secret Delivery releases are preserved. [Active temporary topology](../../../docs/architecture/services-and-workers.md#development-only-live-preview-qa-source-candidate).

`QaMailPrivate.configuration()` returns `null` on unavailable or unauthorized scope, otherwise only the public marker variables `OHMYHOST_MAIL_GATEWAY_URL`, `OHMYHOST_MAIL_KEY`, `PREVIEW_ACCEPTANCE_KEY`, and the scoped `OHMYHOST_PROJECT_ID` and `PREVIEW_MAIL_RECIPIENT`. Its markers satisfy the fixture contract and do not authorize the actual gateway. Call it only from trusted spike code, and provide the returned values to the exact fixture's local workerd configuration. The recipient is intended for that fixture; it is not a credential.

The authenticated control route forwards the original POST request for `/__spike/sessions/{sessionId}/mail-permit` and calls `arm(request, sessionId)`; its JSON body is exactly `{ "id": "..." }`. The private Worker independently checks the operator bearer, fixture session, Dev grant, credit and the current exact project/environment mail key. It stores a two-minute permit bound to one session, container generation, message ID and fingerprint of the entire scope and private credential hashes. Only a matching message to the one recipient is eligible.

After verifying the signed preview hostname, the spike must call `gateMailIngress(request, env, sessionId)` for every request to this fixture. It returns either `{ request }` or `{ response }`. The gate strips caller Authorization, inserts the public acceptance marker only for an armed exact `/api/mail` POST, and never forwards the operator bearer. It permits encoded `@`, `[` and `]` only in a GET or HEAD request for a single JavaScript filename under `/_next/static/chunks/`, passing the original URL through unchanged; encoded API paths and other escapes remain rejected. Export `QaMailIntercept` from the spike Worker and register the exact `qa-mail.invalid` HTTPS intercept before catch-all egress with trusted fixed `{ sessionId, generation }` props. It calls `QaMailPrivate.send(request, props)`. The guest never obtains any Worker or Durable Object binding.

Permit consumption atomically moves to `in_flight`, so parallel duplicate attempts cannot both start. A validated gateway `accepted` receipt permits the second identical ID for the fixture's idempotency check. A real gateway `uncertain` receipt is returned unchanged but locks the permit. A lost or malformed reply, timeout, or cancellation after dispatch returns `409 { "code": "qa_mail_outcome_unknown" }` and locks the permit. The current customer mail SDK maps this response to a non-retryable invalid-response error; the fixture displays an HTTP error rather than a structured unknown receipt. No automatic retry or rearming is allowed for `in_flight` or `unknown`, even after TTL. Reconcile the original message and gateway outcome before disposing of the exact session. The gateway may have accepted a send even if its response was lost.

The authenticated control route can call `QaMailPrivate.status({ sessionId })`. It returns `null` for no permit or exact `{ id, generation, state, attempts, expiresAt }`, where state is `ready`, `in_flight`, `accepted`, `unknown`, `exhausted` or `expired`. An invalid input, failed RPC or malformed result throws `qa_mail_status_unavailable`; it is not evidence that no permit exists. No recipient, scope hash or secret is returned. After successful exact-session sandbox retirement, trusted lifecycle code calls `QaMailPrivate.cleanup({ sessionId, generation })`; it returns exactly `{ deleted: boolean }`. It removes only a matching unused or accepted permit and treats an absent record as already deleted. A generation mismatch, `in_flight` or `unknown` returns `false` and preserves the record for reconciliation. Invalid input or RPC failure throws `qa_mail_cleanup_unavailable`.

For the separate `next-native-auth` fixture, `buildQaMailGatewayConfig(base)` generates a temporary overlay of the complete canonical Development mail gateway profile. It adds the `QA_STABLE_PREVIEW_AUTHORITY` binding to the private Auth QA Worker / `QaStablePreviewAuthority` and the explicit Development-only enable flag while retaining all existing services, settings and schedules. Write the overlay beside the canonical profile so its relative `main` remains correct. The canonical gateway profile stays free of disposable QA bindings, and the new private `NativePreviewAuthMailService.sendNativePreviewAuthMail` is disabled unless the overlay flag and Development environment are both present. Inject its `QA_NATIVE_PREVIEW_MAIL_SCOPE` through the private secret store, not the overlay or receipts. The secret is an exact JSON object containing `platform: "development"`, `fixture: "next-native-auth"`, `organizationId`, `projectId`, `environmentId`, and `recipients` as an array of two to eight distinct operator-authorized addresses. This bounded list can preauthorize two fresh aliases for each of the four instance-type journeys; each journey still uses exactly two fresh users. The trusted Native Auth runtime binds that named entrypoint and passes `{ organizationId, projectId, environmentId, previewId, authGeneration, kind, to, url, messageId }`. Only verification and password-reset messages to an exact listed recipient are allowed. The service checks the current exact QA preview identity and actual Core sender before dispatch, validates the exact preview URL and allowed redirect policy, rechecks both snapshots, and uses the existing mail sender, custody and billing. A send that starts and then loses its reply or authority is `uncertain`; it is never automatically retried by this service. Restore and verify the canonical Development gateway version before deleting the QA Auth Worker; preserve existing credential material under the repository's credential rules.

Hosted configuration and synthetic database/Auth observations do not establish application-mail delivery. Separate authorization checks cannot recall a message after a gateway or provider call has started. A real accepted receipt and exactly one matching inbox delivery are required for the Mail result; the dated checkpoint distinguishes actual provider writes and readbacks from the still-pending ingress fix and delivery journey.
