# Development QA Native Auth

The source connects a private QA authority, a Development-only Native Auth entrypoint and the bridge to the spike Worker's trusted lifecycle, ingress and guest binding. These QA services have not been deployed or exercised against a hosted account. Local tests use synthetic Core and mail authorities; a real temporary PostgreSQL test exercises two signup, verification and login flows, cookie isolation, Auth generation rotation and a pre-commit authority failure. These tests do not establish hosted mail delivery, real project authority, sleep/wake continuity or G1/G2 acceptance.

`authority.mjs` is a separate Development Worker whose `QaStablePreviewState` Durable Objects persist the preview scope and an independently managed Auth generation. Its read-only `QaStablePreviewAuthority` checks the saved scope against the seven-fixture manifest, the actual Core `DevAccessRuntime.authorizeDevAccessSession` owner/grant/epoch predicate, and `NativeAuthRuntime.resolve` for the active project, Dev realm, source, registration/storage, Paid and runtime-credit decisions on every read. This is an isolated QA record, not a product Core schema or the old commit-scoped lease. Current Core Native authority requires a real Native-capable active source deployment, approved realm origin and ready registration; the operator must verify these separately for the exact QA project.

Only the trusted spike lifecycle may bind `QaStablePreviewManagement`. `create(scope)` accepts the exact tuple below without `authGeneration`, persists it and returns `{previewId, authGeneration: 1}`; an identical retry returns the current identity. `rotate({previewId,authGeneration})` compares and increments that independent generation. `revoke(identity)` terminally invalidates an existing exact generation. `retire(identity)` also writes a terminal tombstone when creation has not yet reached the state object, so cleanup after a lost create reply wins over a delayed create; it is idempotent for the exact generation and refuses a mismatch. A retired preview ID cannot be recreated. No source commit, idle deadline or container generation selects a signing key. URL rotation must mint its new capability identity and retire the old record; Auth-generation rotation alone changes the signer, not the URL.

`QaStablePreviewAuthority.resolve(identity)` returns the strict bridge DTO: `platform`, `organizationId`, `projectId`, `environmentId`, `region`, `previewId`, `previewOrigin`, `authGeneration`, `devAccessEpoch`, `revocationEpoch`, `configurationRevision`, `enabled`, `sourceCapable`, `paidAllowed` and `runtimeAllowed`. `resolveForNative(identity)` returns the same current realm policy plus the isolated preview origin and identity to the Native runtime. Neither entrypoint exposes management or credentials. The preview origin is the exact capability origin registered by trusted lifecycle, never a deployed application's origin or a caller-selected HTTP header.

Native's private `NativePreviewService` exposes `fetchStablePreview(request, identity, client)` and `validateStablePreviewSession(identity, cookie)`. It requires the explicit Development-only flag and QA authority binding. It derives the signer from the private realm secret and persisted preview ID/Auth generation, uses `__Host-omh_native_preview_<previewId>.*` host-only cookies, and rechecks current QA authority and the exact Core registration directly inside the existing PostgreSQL entry and pre-commit fences. Native realm and user epochs remain in force. Only the five fixture routes are exposed; social login and invitations remain disabled in this QA path. Verification mail goes to the separate private `NativePreviewAuthMailService`, which independently checks the preview and verified sender and allows only the two to eight explicitly configured QA recipients. Each instance-type journey uses two fresh users; the bounded list can preauthorize all four journeys.

The deployment cohort, in dependency order, is: current Development Core with `NativeAuthRuntime`, `DevAccessRuntime`, `GatewayCreditRuntime` and the separately scoped `PreviewQaDatabaseAuthority`; the QA Auth Worker from `authority.wrangler.jsonc` with a verified private `SPIKE_QA_MANIFEST`; the Development Mail Gateway with its preview authority binding and `QA_NATIVE_PREVIEW_MAIL_SCOPE`; the Development EU Native runtime with the QA authority and preview-mail bindings; then the trusted spike Worker and its bridge. `buildQaNativeRuntimeConfig` produces a validated temporary overlay of the complete current Development EU Native profile, adding the flag and two exact service bindings without modifying the canonical profile. Write that overlay beside the source profile so the relative `main` path remains correct. Production profiles do not bind these QA services or enable the flag. Supply the manifest and recipient scope through trusted deployment configuration, never the guest. Preserve existing custody credentials and full Worker bindings when deploying any version. Restore and verify the normal Native and Mail versions before deleting the temporary QA Worker.

## Bridge contract

- `handleQaAuthPublic` runs in trusted ingress before the guest. It forwards only the five fixture paths, checks the exact preview origin, requires POST Origin and rejects every supplied foreign Origin, bounds request bytes and strips forged platform/proxy/IP/authorization headers. The client address comes from trusted ingress. An already-aborted request cannot dispatch.
- `QaNativeAuthSessionOutbound` is the guest session-validation service. Trusted Durable Object props set its `scope`; guest paths, headers and bodies cannot select scope. It accepts only `POST http://preview.capabilities/native-auth/session`, a bounded cookie header and an empty body. The tagged response has only the documented session fields.
- The immutable scope contains `platform: "development"`, `fixture: "next-native-auth"`, organization, project, environment, `region: "eu"`, handle, Dev origin, principal, Dev-access epoch, preview ID, exact preview origin and positive `authGeneration`. It must match the verified seven-fixture `SPIKE_QA_MANIFEST`.
- Each bridge call checks current QA authority, Dev grant and credit before and after the Native RPC. It restricts response cookies to the exact preview prefix with Secure, Path=/, and for the session token HttpOnly and SameSite=Lax or Strict. Cross-origin redirects are refused. A failure before dispatch is unavailable; after dispatch a lost reply, backend server failure, invalid response, abort or changed authority returns HTTP 409 with `{ error: "qa_auth_outcome_unknown", outcome: "unknown", retryable: false }` and no backend data or cookies. The adapter does not retry.
- Only Native holds its registry and signing credentials, and only Mail holds sender credentials. Never put them into the guest, source, control requests or receipts. The application necessarily receives its own browser cookie on application requests.

The authority and transaction checks are fresh checkpoints across separate services; they are not a distributed transaction and cannot undo a mutation already committed when a later revocation or lost response is observed. The manifest and synthetic doubles do not prove live QA ownership, physical data assignment, sender verification or delivery.
