## D621 Paid domain repeats and conflicts

<a id="d621"></a>

### D621: repeats are answers, and conflicts name their cause

Recorded from the review of CORE-39 on 15 November 2026. The repeated-delete answer is the owner's proposal; a fresh idempotency key is a new attempt, never a reused key.

- A fresh key from the same member for the same hostname's live connection (`awaiting_deployment`, `pending` or `active`) is the same request. Apply answers that connection as it stands (200): no database write and no route, custom hostname or DNS change; an active or pending connection is read from its provider state as the status read does. Only the original key activates an `awaiting_deployment` connection after its Prod deployment.
- A repeated delete of an already deleted connection answers the deleted state (200), under its own key or a fresh one. It opens no native-auth policy operation: the first delete's operation is the only one, and its completion settles it once.
- `domain_already_configured` (409, not retryable) names a live connection of another hostname or of another member. The only path is to delete that connection to replace it. `domain_deleting` (409, not retryable) names a connection still being deleted under another key.
- `idempotency_key_reused` (409) remains for a used key whose apply request changed, whose connection has since ended, or whose delete request changed.

The request digest covers the method, the path, the organization, the actor and the body. The same member repeating the same hostname is therefore one request under two keys, and refusing it as another connection told customers to delete a working domain. The store answers the replay before any claim write, and the Worker returns that connection without provisioning, because its receipts belong to the key that created it. The store and the Worker must be deployed together, store first, because the apply response carries `sameConnection`. [Storage and domains](../storage-and-domains.md).
