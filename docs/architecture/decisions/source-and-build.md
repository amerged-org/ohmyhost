## D435 Next.js security floors of 22 October 2026

<a id="d435"></a>

**State:** implemented with the fixture, tests and Skills and released on 23 October 2026 through the [D429](delivery-and-operations.md#d429) policy cohort to Development and then Production (both accepted); the public clients, documentation and website that quote the floors follow in their own releases. **Decision:** the Next.js floors of [D032](#d032) rise from 15.5.27 and 16.3.8 to the single floor 16.4.1, and the 15.x floor is dropped (owner decision of 23 October 2026) because the pinned OpenNext cannot build Next.js 15: a floor of 15.5.28 would send a customer to a failing build. The advisories published on 22 October 2026 affect every earlier release of those lines: [GHSA-2464-fhr4-w9xw](https://github.com/vercel/next.js/security/advisories/GHSA-2464-fhr4-w9xw) (critical, remote code execution through the Image Optimization API with SVG and an upstream `sharp` before 0.35.5; fixed in 15.5.28 and 16.4.1), [GHSA-673q-mjm6-r5xr](https://github.com/vercel/next.js/security/advisories/GHSA-673q-mjm6-r5xr) (critical, remote code execution through `use cache` functions that return typed arrays; Next.js 16 only, fixed in 16.4.1) and [GHSA-p3m5-59mp-jv5r](https://github.com/vercel/next.js/security/advisories/GHSA-p3m5-59mp-jv5r) (high, denial of service through Server Actions; fixed in 15.5.28 and 16.4.1). Each has a fixed release, so the denied ranges stay empty and there is still no upper bound. Admission refuses every Next.js 15 release and 16.0.0 through 16.4.0 with `framework_version_unsupported` and the minimum 16.4.1, and admits 16.4.1 and later. Admission is the only gate: an application on a refused release moves its package.json and lockfile to the reported minimum before its commit can be planned or built, and a push to a connected repository ends as `auto_deploy_plan_rejected` ([D040](#d040)) until it does. A deployment that is already built and running is untouched until its source is planned and built again. Promotion and rollback activate an already built immutable artifact without source admission, so a Development artifact built on a refused release can still be promoted and Production can be rolled back to an earlier vulnerable artifact; whether they must re-check the floors, and whether the owners of live deployments built on a refused release are notified, are open owner decisions, not part of this change. The standalone fixture follows with `next` 16.4.1 ([D425](delivery-and-operations.md#d425)), and the shared corpus, the tests and the Skills move with the floors. The floors file is a D429 policy source that the BuildRunner image copies, so SourceFetcher, BuildRunner with its build Containers and Control ship it as one cohort per environment, Development before Production: a partial rollout makes their policy copies disagree, which Control and the build image report as a platform fault instead of a customer message. The CLI and MCP clients carry the floors with their next release. Next.js 15 builds stopped on 21 October 2026, when the pinned OpenNext started refusing Next.js 15 as an unsupported major. [Current architecture](../build-and-deploy.md#source-admission), [floors](../../../packages/contracts/src/framework-build-script.mjs), progress.

## D467 Customer code never runs outside the limits and egress policy

<a id="d467"></a>

**State:** implemented in source and unit-tested at the `dispatch.get` call; not proven on a real Workers for Platforms namespace. **Development acceptance is required before release**, because a failing probe would block every deployment. **Finding:** the deploy health probe in `apps/wfp-management` ran the candidate through a `WFP_DISPATCH` binding with no outbound service and no options, so for a probe window (four attempts of five seconds per activation) the candidate ran with default CPU and subrequest limits, without the origin allow list and the per-project relay limiter, and could open sockets (Cloudflare documents `connect()` as disabled only for a Worker that an Outbound Worker applies to; this change did not verify that on a live account). A tenant could branch on the host `candidate.internal`; no cross-tenant gain was found.

**Decision:** (1) `WFP_DISPATCH_LIMITS` and the egress context version live once in `@ohmyhost/contracts/wfp-dispatch`; the gateway, the functions scheduler and the probe import them. (2) Every `wfp-management` profile declares its namespace's gateway outbound service with the `EGRESS_CONTEXT` parameter (Development `ohmyho-wfp-egress-v3-poc-private-fullstack`, Production `ohmyho-wfp-egress-production`, the disabled placeholder for the default profile); the sandbox namespace has no Outbound Worker and borrows Development's, a choice the owner may revisit. (3) The probe passes `{version: 1, projectId, allowedOrigins}` from the validated scope and `runtimePolicy.egressAllowedOrigins`, the list the gateway receives for the route (activation compares them), so a health check behaves as under live traffic; its success criteria, retries and excerpts are unchanged. A deny-all probe was not needed because the context is available. (4) Planning refuses `cloudflare:sockets` in any module as `socket_primitive_unsupported`, whatever the configuration. SourceFetcher decides from the decoded specifiers that its Babel-based reachable walk parses, so an escape in the specifier, a regex literal or any module-loading form (static import, re-export, `import()`, `require`) cannot hide it. `ohmyhost init` cannot parse, so it only hints from the raw text with string escapes decoded; a comment, a type-only import or a variable holding the specifier is a false positive there. The rule is defence in depth, not the control: it misses a specifier built at run time, a dependency or workspace package, a module the walk cannot resolve and static runtimes, and it allows `node:net` and `node:tls`. The Outbound Worker is the control. (5) A CPU-limit exception from the probe, recognised as the gateway recognises it, is the verdict `unhealthy` with status 429 and the gateway's sentence from the shared module, within the existing health contract; a subrequest-limit error is not distinguishable from other exceptions and stays unknown. (6) The gateway, the functions scheduler and the probe build `EGRESS_CONTEXT` with the shared `buildEgressContext`, the scheduler uses the shared limits, and a test feeds the probe's recorded context to the real outbound Worker. The admission change alters the policy fingerprint, so SourceFetcher, BuildRunner with its Containers and Control release together ([D429](delivery-and-operations.md#d429)). ## D501 Four open builds per organization

<a id="d501"></a>

**State:** released to Development and Production on 14 November 2026. **Context:** No organization may occupy every build sandbox with its open reservations. **Decision:** a reservation counts toward the cap of four while its operation is queued or running and either its build started within the last 60 minutes or it is unstarted inside its start window. The claim re-checks the count in the same batch as the new reservation, and a fifth claim is refused with `build_capacity_reached` (429, not retryable) before anything is reserved. **Consequence:** a settled build frees its slot at once; a crashed started build stops counting after 60 minutes.

## D502 Streamed archive inspection under retention budgets

<a id="d502"></a>

**State:** released to Development and Production on 14 November 2026. **Context:** A bounded read forward keeps memory independent of the expanded archive size, so each body is kept only under a budget. **Decision:** the inflated tar is read forward once. A body is kept only when a rule reads it: inspection, companion and Worker files, lockfiles and tsconfig files within 16 MiB together; Next.js runtime source under its own file and byte limits; and other source and JSON files of at most 256 KiB within one shared 32 MiB budget. A body that is skipped and later reached by a traversal is a limit refusal. The Next.js runtime-source limits apply only once the application is detected as Next.js. **Consequence:** the traversal limits bind only the files it reaches, and the memory of an archive is bounded by the budgets rather than by its expanded size.

## D508 Exhausted managed publication ends with a dispatch failure

<a id="d508"></a>

**State:** released to Development and Production on 14 November 2026. **Context:** A sealed publication that can never dispatch would block every later source write. **Decision:** the project publisher calls `sweepExhaustedManagedSourceDispatch` before it claims more managed-source work. The sweep finds one such publication whose event is unclaimed and reconciliation-marked, ends the publication and its operation with `MANAGED_SOURCE_DISPATCH_FAILED` (public `managed_source_dispatch_failed`), and reports whether it did. A queued initialization whose event exhausted without a child publication fails the same way ([D573](#d573)). Wave 4 extends the same sweep to a dispatch acknowledged more than 30 minutes earlier that is still unfinished ([D627](#d627)). **Consequence:** the source is unblocked. Whether the change landed is not decided by the sweep; the caller reads the current source and submits the change again only if it did not land.

## D509 Rollback and promotion mutually exclusive per environment

<a id="d509"></a>

**State:** released to Development and Production on 14 November 2026. **Context:** A rollback carries no head, so it must not run while a promotion of the same environment is open. **Decision:** the acceptance of a rollback is refused while a promotion of the environment is queued or running, and the acceptance of a promotion is refused while a rollback is, each by a `precondition_changed` guard in the acceptance batch. **Consequence:** the second command is refused until the first one ends; nothing is queued behind it.

## D510 GitHub installation revoked only on 404

<a id="d510"></a>

**State:** released to Development and Production on 14 November 2026. **Context:** Only GitHub's answer that an installation does not exist ends the connection; a rejected credential or a suspended installation must leave working custody in place. **Decision:** only `GithubInstallationNotFoundError`, which the installation lookup raises on a 404, revokes the connection; other failures leave it unchanged. A pushed tag is no branch of any configured target and is acknowledged as `ignored` (`branch`), so it does not stall the auto-deploy queue. **Consequence:** a removed installation is still detected; a suspended one is reported as a failure instead of a revocation.

## D511 Per-project limit on the legacy props path

<a id="d511"></a>

**State:** released to Development and Production on 14 November 2026. **Context:** The legacy props path has no limit of its own, so the project's gateway limit must apply before the Core is reached. **Decision:** the handler calls the project's gateway limiter (`GATEWAY_RATE_LIMITER`, keyed by project) before it reaches the Core; a refusal, a missing limiter or a failing limiter answers 429 `rate_limited`. **Consequence:** a project's legacy calls share the limit of its gateway traffic; the limiter's own failure closes the path rather than opening it.

<a id="d573"></a>

**State:** released to Development and Production on 14 November 2026. **Context:** The dispatch sweep ended only exhausted sealed publications. A queued initialization whose initialization event used every delivery and was never acknowledged kept its recipe queued, so the source reported its initialization as pending indefinitely. **Decision:** the same sweep fails such a recipe with `MANAGED_SOURCE_DISPATCH_FAILED` (public `managed_source_dispatch_failed`) when it has no child publication, because the initialization then never started and no child publication exists. The update is guarded by the recipe still being queued without a child, so the sweep does not select it again; the event stays unacknowledged. **Consequence:** the source reports the failure, the caller reads the source and may start the explicitly chosen template again under a new key, as the [deploy skill](../../../skills/ohmyhost-deploy/SKILL.md) describes.

## D627 Stalled acknowledged managed-source dispatch fails after 30 minutes

<a id="d627"></a>

**State:** implemented in source; release pending. **Context:** The Queue consumer retries a managed-source message every 30 seconds for at most 30 retries and then dead-letters it, and nothing reads the dead-letter queue. The dispatch is acknowledged when the send succeeds, so an outbox event that was acknowledged never reaches the exhausted state D508 and D573 detect: a sealed publication stayed sealed, blocking every later managed-source write, and a queued initialization stayed queued. An unrecoverable object or immutable receipt mismatch is retried by the Queue as well and never ends by itself. **Decision:** the same sweep ends a sealed publication, and a queued initialization without a child publication, whose dispatch acknowledgment is more than 30 minutes old, with `MANAGED_SOURCE_DISPATCH_FAILED`. Thirty minutes outlive all thirty-one deliveries, so a mismatch that stays unrecoverable ends after the bounded number of attempts. **Consequence:** a source stalls at most 30 minutes after its last delivery. A publication whose commit reached Git before its state was recorded is reported as failed; the caller confirms the landed change with `source_get`, as D508 already states. An initialization whose child operation exists but was never attached can be ended while that child is still open, so the child may still commit after the recipe reports failure; this residual risk is accepted with the bound.

## D629 Customer egress allow-list of at most 11 origins under the 16-origin cap

<a id="d629"></a>

**State:** implemented in source; release pending. **Context:** The platform adds up to five origins to an application's egress policy: mail, the storage gateway, R2, the AI gateway and the browser gateway. The customer schema still admitted 13 origins, so an application with 13 customer origins and all five platform origins (18) was refused at staging, after the billed build, with a generic input error. **Decision:** the schema admits at most 11 customer origins, so 11 + 5 = 16 fits the existing cap at every site that enforces it, including the Core database CHECK on `shared_gateway_route_revisions` (migrations 0334 and 0336). Raising the cap to 20 would need a Core rebuild of that table and is not part of this decision. **Consequence:** an application that declares 12 or 13 customer origins is refused at parse time and must drop origins; this is the intended breaking change of early development.

### D602 follow-up — 18 November 2026: outbound request deadline
