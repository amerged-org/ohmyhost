## D628 Switched data change abandoned 24 hours after its switch

<a id="d628"></a>

**State:** implemented in source; release pending. **Context:** The lease sweep excluded a data change whose data assignment had switched for as long as it stayed unreconciled, so its provider claim was never released and one such change blocked every later provider mutation of its project. **Decision:** the sweep holds a switched data change for 24 hours after its `assigned_at`, which keeps D277's claim and replay through an explicit `:reconcile`. Once the 24 hours have passed, the sweep abandons it as `OPERATION_ABANDONED` and releases its provider claim, and the failure message and the audit reason name the switched data change. A switch that commits after the candidate was read still aborts the recovery batch while it is inside the hold. **Consequence:** no project stays blocked by a switched data change longer than 24 hours. The retired Dev database and files of an abandoned change are not purged by that operation, so their purge bookkeeping strands; the owner accepted that trade-off for the bounded block. A `:reconcile` that arrives on day 24 can race this sweep: the sweep sets the operation's workflow run `completed`, so a reconcile that reaches the run afterwards finds no pending recovery and does not replay the change.

## D512 Thirty-day quarantine of released project handles

## D513 Absence proof before a spent bucket reservation is released

<a id="d513"></a>

**State:** released to Development and Production on 14 November 2026 (Core migrations [0665](../../../apps/control-store/migrations/core/0665_r2_bucket_absence_evidence.sql), [0666](../../../apps/control-store/migrations/core/0666_r2_spent_reservation_absence.sql) and [0720](../../../apps/control-store/migrations/core/0720_r2_reservation_failure_release.sql)). **Context:** A read taken before a spend cannot show that a create made by the spend did not produce the bucket, so only a read after the spend can release the reservation. **Decision:** the runtime reads the bucket before it authorizes a create and hands that observation to the create, so no read follows the authorization. When a spent reservation is found on a later pass, the runtime records a provider absence as append-only evidence and releases the reservation only if that evidence was observed after the spend; the claim row leaves with it, and an operation that has not ended answers `operation_open` and keeps the reservation. An unspent reservation needs no evidence once its operation has ended ([D570](#d570)). **Consequence:** a spent reservation is never released on a read that could predate its create, and the target can be reserved again only once its operation has ended.

## D514 Recovery of uncertain final Queue sends

<a id="d514"></a>

**State:** released to Development and Production on 14 November 2026. **Context:** A publisher can lose its final lease after claiming an event and before creating its run, and a final send can be uncertain; both outcomes must be recoverable in the event's own lifecycle. **Decision:** the final codes of a parked delivery are the lease-expired code and `PRODUCT_COMMAND_QUEUE_SEND_UNCERTAIN`. The handoff covers every Workflow run type: source link, rollback and promotion are handed off in an active project with no cleanup run; a deletion only while its project is deleting, and a data change only while it is active, each with its cleanup run still open. A candidate is found only in a queued or running operation. The replay candidate's handoff runs before the run-less acceptance, and the handoff records the audit type `ProjectDeletionQueueDeliveryRecovered`, unchanged for every type. An exhausted run-less event of any of the five types is accepted at its current attempt so the ordinary handoff matches it. A reconciliation request with nothing pending answers `reconciliation_not_pending` (409, not retryable). **Consequence:** an event is recovered only in the lifecycle of its own type, and an unmatched request is no longer an internal error.

## D515 Versioned key ring for database registry credentials

<a id="d515"></a>

**State:** released to Development and Production on 14 November 2026. **Context:** Credentials sealed under one fixed key version need bulk re-keying for a rotation, while a key ring lets a rotation proceed credential by credential. **Decision:** the environment's registry reads an optional current key version and an optional previous key with its version. The current key seals every credential, the previous key only opens credentials sealed under it, and each such credential is re-sealed under the current key when it is read; the re-seal never overwrites a credential that changed meanwhile. **Consequence:** a rotation needs no bulk re-keying, and a credential under a version that is in neither slot is unavailable.

## D516 Session cookies with the \_\_Host- prefix

<a id="d516"></a>

**State:** released to Development and Production on 14 November 2026. **Context:** Native session cookies must be bound to the exact host that set them, and the realm must read only that token. **Decision:** the engine writes its cookie names with the `__Host-omh_native` prefix, `Secure`, `Path=/` and no `Domain`, and the realm refuses any cookie other than the native session token (`__Host-` or `__Secure-` prefixed, or bare) before it performs authority or limiter work. **Consequence:** the cookie is host-only, and the realm reads only the session token that its own host set.

## D570 An ended operation's bucket reservation leaves with its claim

<a id="d570"></a>

**State:** released to Development and Production on 14 November 2026 (Core migration [0720](../../../apps/control-store/migrations/core/0720_r2_reservation_failure_release.sql)). **Context:** The failure path of an operation deletes its provider mutation claim in the same batch that fails the operation ([deletion](../../../apps/control-store/src/catalog/provisioning/deployment-failure.ts#L305)). A bucket reservation references that claim with `ON DELETE RESTRICT`, so the claim could not leave, the operation could not end, and the reservation could never be superseded. **Decision:** deleting the claim of an operation that has succeeded, failed or been cancelled first deletes the reservation of that claim, inside the same delete and before the reference check. The reservation's own delete rule still decides what may leave: an unspent reservation (`create_started_at` NULL, which is written once, before the only provider create) may leave without absence evidence, because it could never have created a bucket; a spent reservation leaves only with a bucket receipt or with absence observed after its spend. A spent reservation that cannot leave aborts the whole claim delete, so its operation stays open until a read after the spend supersedes it. A running operation keeps both its claim and its reservation. **Consequence:** an operation whose bucket was never created ends on its failure path instead of waiting for a supersede; no spent create is released on a read that could predate it.

## D571 A retried supersede answers its committed outcome

<a id="d571"></a>

**State:** released to Development and Production on 14 November 2026. **Context:** A supersede deletes the reservation and its claim in one batch. If its reply is lost, the retry finds both gone and, before this decision, answered a conflict for an outcome that had already been committed. **Decision:** `supersedeR2BucketReservation` answers `superseded` when the reservation has left, the absence evidence for the claim's bucket exists and no bucket receipt was made for the claim. The evidence table has no operation identifier, so the match is by organization, project, environment and claim. A claim with a receipt keeps the conflict answer. **Consequence:** a retried supersede reports the release that committed; the release is not repeated, and no other state is reinterpreted as success.
