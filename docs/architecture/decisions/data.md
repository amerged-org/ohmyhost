## D441 PGCF targets, session transport and controlled provider cutover

<a id="d441"></a>

Status: **Implemented in source; exact release and live cutover pending** (W01, 2026-10-26).

The provider adapter owns only the generic PGCF Management API. OMH persists append-only target revisions and explicit current heads per physical data environment, preserving logical Dev/Prod authority and Neon history. A provider switch requires the approved manifest, previous registration and lifecycle versions, role/import/recovery receipts, a new registry generation and an owner-only activation record. Old pools and bindings cannot retain access to the former provider. `OHMYHOST_DATABASE` remains the customer contract; session-preserving WSS is selected from trusted PGCF metadata for application connections, with optional unactivated Control support, no PGCF Hyperdrive and no error-driven provider fallback. Both Controls retain the exact Neon SQL allowance under D444.

Five fixed sizes replace CU autoscaling for PGCF; future projects retain their selected US/EU database region. Smaller nominal storage requires a separate migration; Paid loss does not shrink data. Above-Free databases lose wake eligibility through a confirmed manual suspension, with durable idempotent recovery and restoration only for this policy's own unchanged operation/generation after entitlement returns. Power requests use a provider-enforced expected-generation precondition; an intervening operator change cannot become the policy's restoration authority. The native awake-memory meter remains authoritative and is billed hourly by the credit service ([PGCF memory](../billing-and-pricing.md#pgcf-memory)). The approved US metadata transition uses an exact frozen inventory and retains original R2, Git and artifact placement. Temporary SQL credentials inherit only their intended role with `SET ROLE` disabled; private export authority stays separate. Under the owner's [D444](#d444) amendment, twelve application databases need the bounded real import, recovery, binding and application-provider traffic-retirement gates. The implemented optional Control WSS path does not authorize moving Control: both Control databases remain on Neon while their separate D1 design proceeds.

## D446 Database events, schedules and execution billing

Status: **Implemented in source; release and live acceptance pending** (W34, 31 October 2026).

<a id="d446"></a>

PGCF delivers webhooks, runs schedules and counts executions; OMH owns the customer contract. Each operation resolves the environment's single PGCF database through the compute scope and accepts a webhook, schedule or usage row only when it belongs to that database and to OMH's PGCF project; a missing or foreign object is absent. Customers never send `database_ids`, `project_id` or `role`. A schedule runs as the environment's runtime role under row-level security, with a statement budget of 1,000 to 30,000 ms. Executions (finished schedule runs and delivery attempts) are counters only (D-3, owner decision of 31 October 2026): they have no meter and no price, and a schedule or a webhook costs the awake compute time of the database, which `pgcf.memory.active` already bills. Seven exact database event types are offered, and remote MCP exposes read tools only.

OMH limits each project and environment to five webhooks, which protects the shared budget. Shared Dev and Prod data lists the same webhooks and schedules. Release and live Development acceptance are not recorded yet.

Data events come only from the platform's `pgcf.capture(columns)` trigger: a table watch attaches it through the environment's migration role, and one migration form declares the same trigger. ## D466 Read-only direct credentials are enforced by privileges

Status: **Implemented in source; release and live acceptance pending** (security fix, 6 November 2026).

<a id="d466"></a>

An independent penetration test on an isolated Development database found that a `mode=read` direct credential was not read-only. The login was a member of the read-only role with the session default `default_transaction_read_only=on`, and a login can switch that off for its own session. The remaining boundary was privileges, and PostgreSQL's defaults leave three holes for every role: PUBLIC holds TEMPORARY on the database, so a read login could fill the shared volume with temporary tables; PUBLIC may execute the `pg_catalog` large-object creators `lo_create`, `lo_creat` and `lo_from_bytea`, so it could leave persistent large objects, which also keep a temporary role from being dropped; and PUBLIC may execute both `pg_logical_emit_message` signatures, so a SELECT-only login could write WAL records of up to 1 GB per call without a limit (measured), which fills the volume the same way.

Decision: the session default is a convenience and never the boundary. Every migration runs, through the database owner `app` (no superuser, no CREATEROLE), `REVOKE TEMPORARY ... FROM PUBLIC` and grants TEMPORARY and EXECUTE on the five functions (the three creators and the two `pg_logical_emit_message` signatures, one list in `PERSISTING_FUNCTION_SIGNATURES`) only to the migration and runtime roles, so existing environments are fixed by their next deploy or migration, or earlier by the next `read` credential issued for them ([D462](#d462)). Only a superuser changes a `pg_catalog` function ACL, so PGCF's baseline revokes the five functions from PUBLIC and grants them to each database's owner role WITH GRANT OPTION (the owner's GRANT is a no-op while PUBLIC still holds them or while the owner holds them without a grant option, and a `DO` block contains the `insufficient_privilege` error it raises when PGCF revoked them from PUBLIC and the owner holds none, so no migration aborts). Before returning a read credential, `issuePgcfDatabaseAccess` proves on the real login that it holds no TEMPORARY or CREATE on the database, no CREATE on any non-system schema, no EXECUTE on any of the five functions and no INSERT, UPDATE, DELETE, TRUNCATE or sequence USAGE/UPDATE on any user relation; a violation throws `ProjectDatabaseAccessError("scope")` and the existing failure path drops the new role. Write credentials are unchanged and keep temporary tables, large objects and logical messages through the runtime role.

Release order: the PGCF baseline first. A read credential is refused until PGCF's baseline covers all five functions; it is reported as unavailable. An existing environment needs no deploy for it, because issuing the credential runs the owner grants first ([D462](#d462)). A refusal logs a fixed-code line naming the failed checks, so an operator tells it from an outage. Write credentials are unaffected before the baseline, but not in the window after it: once PGCF revokes the five functions from PUBLIC, the migration and runtime roles lose them until that environment's next migration re-runs the owner grants, and a customer application that uses large objects or logical messages, or a `write` psql session, gets 42501 meanwhile. This second half is only half closed: an environment's roles get the functions back at its next migration or at the next `read` credential issued for it ([D462](#d462)), and an environment that has neither stays without large objects and logical messages for its runtime and `write` logins until the operator sweep over every environment, which does not exist, runs. A customer `SECURITY DEFINER` function is out of scope for the platform: PUBLIC may execute it by default, admitted migrations refuse GRANT and REVOKE, and a default revocation would break RLS helper functions, so the customer Skill and the [database chapter](../database.md#roles-migrations-and-application-rls) tell customers to prefer `SECURITY INVOKER` or to check inside the function that `session_user` can use a runtime role, which admits the hosted runtime and `write` access logins and refuses `read` ones.

Sources: [bootstrap](../../../packages/platform/src/modules/database-migrations/role-grants.ts), [read-credential proof](../../../apps/neon-management/src/pgcf-access.ts), [privilege tests](../../../apps/neon-management/test/read-credential-privileges.integration.test.ts), [database chapter](../database.md#customer-sql-access).

## D559 A deleted database ends its access roles and webhooks; the access sweep cannot be starved

Status: **Implemented; released to Development and Production on 14 November 2026; live acceptance pending** (security fix, 6 November 2026).

<a id="d559"></a>

The maintenance sweep reads 50 expired and 50 undropped access rows per pass across all tenants, ordered by expiry, and revokes each one. A customer who deleted a project that still had an unrevoked credential left a row whose role deletion PGCF answers with 404 (the audit read PGCF as keeping the database row while answering every role call of a deleted database with 404, the fallback role listing included; live proof is pending). The error escaped, the row stayed unrevoked, and about 50 such rows were the only rows ever selected: no other tenant's expired credential was revoked, so open sessions outlived their expiry and roles piled up towards PGCF's limit of 100 per database. The same deletion left the database's webhook subscriptions in PGCF, where they count against the one webhook cap that every customer shares, and no OMH path could delete them once the target was retired.

Decisions: (1) A database that PGCF reports deleted is the terminal answer for its access roles. `revokePgcfDatabaseAccess` reads the database only when a role call (role deletion, role listing, or the read of a recorded deletion operation) answered 404, or when a recorded deletion operation is still pending; it treats the roles as gone only if the answer is the same database of this PGCF project with desired and observed state both `deleted`. A bare 404 (also from the database read itself), a database still `deleting`, a live database and a failing read keep the access pending and retried. (2) The sweep orders every category by `project_database_access.sweep_attempted_at` first (never tried before tried, migration `0639`) and by expiry or revocation second, and processes the rows in that order. For the expired and undropped categories a stamp counts as a try only when it is later than the access's expiry or revocation ([D575](#d575)). After the pass `markAccessSweepAttempts` stamps, with the pass time, every row the pass tried: a revocation that failed and a credential the budget check kept. A row the 45-second budget never reached is not stamped and stays at the front. So a row that cannot be finished, or is kept, rotates behind every row not yet tried, and another tenant's fresh expired credential is attempted within one or two passes however many rows fail. `readAccessSweep` is a pure read again; the stamp is the only write and uses the `now` the caller supplies (the scheduled time of the pass). (3) `deleteProject` removes the webhooks stored for exactly the deleted database after PGCF confirmed the deletion and before `retireTarget`; every database retirement (project deletion and data-mode change) runs through it. A 404 on a webhook deletion counts as deleted. A refused deletion, or a listing beyond 50 pages, returns `reconciliation_required` with the target active; a webhook the strict parser rejects is skipped with the fixed line `database_webhook_cleanup_skipped` (a count only) and is never deleted.

Unproven live: the PGCF answers this rests on were read by the audit, not observed. If PGCF answers a deleted database's reads with 404 instead of a row with state `deleted`, rule (1) never fires, those rows keep failing, and the rotation in (2) is what limits the damage: each such row costs one slot per rotation behind every row not yet tried, so healthy credentials are still revoked, but the stuck rows are never retired. A `DELETE` of a webhook of a deleted database that PGCF refuses leaves the deletion in reconciliation. Both need Development acceptance.

Release order: apply migration `0639` to Core before the Control Worker. The sweep orders by the new column, so a Control Worker without it makes the whole sweep throw `no such column` and stops all expiry revocation. An old Control Worker on the new schema is harmless. The management Worker needs the `markAccessSweepAttempts` method of the Control Worker (the same cohort), because it validates its bindings at start.

Not decided here: the credential rows of a deleted project are still revoked by the next sweep (within about 15 minutes), not in the deletion transaction; webhooks that earlier deletions left in PGCF stay until an operator or a later sweep removes them; an organization-wide cap on database webhooks needs a product limit the owner has not set. The mark stays on a row after it succeeds in a later pass, which is harmless because a revoked and dropped row leaves every list.

## D462 Read credentials run the owner grants when they are issued

Status: **Implemented in source; release and live acceptance pending** (security fix follow-up, 6 November 2026).

<a id="d462"></a>

[D466](#d466) fixes an environment through the owner grants of its next migration, so before that migration every `read` credential of an existing environment was refused and, after the PGCF baseline, its runtime and migration roles lost large objects and logical messages. Decision: `issuePgcfDatabaseAccess` calls `ensureProjectRoleGrants` for `mode=read` before it creates the role, because the statements involve only the migration and runtime roles, and a failure of the owner path then leaves no role to take back. It reads the connection of the database owner `app` exactly as a migration does (no superuser, no CREATEROLE), verifies the origin host and that the login is the owner, and reads whether PUBLIC still holds TEMPORARY or the migration or runtime role lacks TEMPORARY or a persisting function, without a lock. Only if something is missing does it run the three statements of `projectSqlPersistenceGrants` (`REVOKE TEMPORARY ... FROM PUBLIC`, `GRANT TEMPORARY` to both roles, the contained `GRANT EXECUTE` of the five functions) in one transaction under the migrations advisory lock. `projectSqlRoleGrants` is built from the same three statements, so the migration and this call cannot drift.

Both writers of these catalog rows now take the same lock: `migrateProject` runs its owner grants through the same transaction too, because two overlapping GRANT or REVOKE statements on one `pg_database` or `pg_proc` row end with "tuple concurrently updated" (XX000) for the later one. A held lock answers `busy`: the issue continues (the proof decides). `migrateProject` retries its owner transaction once after a 10 s pause (`OWNER_GRANTS_RETRY_DELAY_MS`), so a table, watch or short migration that holds the lock never stops a deployment: at most 5 s + 10 s + 5 s inside the 2-minute Workflow step. Only a lock still held then returns `reconciliation_required` with the reason `owner_grants_busy` and nothing applied. What follows is not automatic: the Workflow ends the deployment with `reconciliation_required` (`reconcile` in `apps/orchestrator/src/deployment-workflow.ts`), no step retry or timer re-drives it, and a deployment is not a replay candidate (`workflow-replay-queries.ts` lists only source link, deletion, rollback, promotion and data change); it waits for an explicit `operation reconcile` request, which observes the provider and, when its preflight is safe and nothing is to be abandoned, restarts the original command in a new physical Workflow, at most 32 attempts per operation (`provider-reconciliation-commands.ts`). The outcome is `current` (nothing missing, nothing written), `ensured` or `busy`, and a refused read proof carries it in the log line (`grants`), so a refusal with `current` or `ensured` means the PGCF baseline is missing, and one with `busy` means a migration held the lock and a retry can fix it. An owner that is not `app`, or a wrong origin host, raises the provider conflict and the issue reports `unavailable`. Write credentials never open the owner connection. The statements never remove an explicit grant to the read-only role, so the proof still refuses one. A PGCF baseline run that rewrites the same function rows at the same instant can still collide; it is outside this repository.

The second half of the defect is only half closed. A read credential no longer waits for a deploy. The runtime and migration roles of an environment, which lose large objects and logical messages when the baseline takes the functions from PUBLIC, get them back at the environment's next migration or at the next `read` credential issued for it, and not before; an environment with neither, and its `write` psql sessions, stay without them until an operator sweep over every environment, which does not exist. Such a sweep needs the list of all PGCF-placed environments with their physical environment ids and database ids, an owner decision (a connection wakes a sleeping database, whose awake time is billed, [D446](#d446)) and a bounded, resumable pass over `ensureProjectRoleGrants`; it is not built.

## D575 A budget-kept access counts as tried only after its own expiry or revocation

Status: **Implemented; released to Development and Production on 14 November 2026; live acceptance pending** (security fix, 14 November 2026).

<a id="d575"></a>

The access sweep stamps an access that the budget check keeps, so that a refused credential behind a tenant's admitted ones is reached in a later pass ([D559](#d559)). Such a stamp is written while the credential is still active. If it counted as a try of the expired category, the credential would fall behind every untried expired row of its tenant at the moment it must be revoked.

Decision: for the expired and undropped categories the sweep orders by a stamp only when it is later than the access's `expires_at` or `revoked_at`; the active category, from which the budget check selects, orders by every stamp. A stamp is written when the budget check keeps an access and when a revocation fails, both with the pass time of the scheduled 15-minute run.

Consequence: a kept credential that expires is revoked at its own place among the untried expired rows of its tenant, not after rows that were tried after its expiry. A tenant's untried rows are reached at five per pass, so a refused credential is reached after at most the rounded-up quotient of its tenant's untried rows and five passes, while the category limit of 50 does not bind.

## D604 Durable database webhook subscription generations

Status: **Released in 0.1.57; scoped US/EU hosted acceptance passed** (15 November 2026).

<a id="d604"></a>

The legacy webhook create calls PGCF with an idempotency key derived from the tenant and request, but checks the five-webhook limit before asking PGCF for a replay. The legacy source now refuses that answer, while the cap/replay limitation remains for that API.

Decision: the additive subscription API accepts a client-chosen ULID and explicit positive activation generation. Generation 1 reserves a scoped Core receipt before provider I/O. An identical authorized activation request and key recover the same active generation's secret even at capacity. A changed request or a late old-generation receipt is refused. The next generation starts only after confirmed deactivation and uses a distinct provider idempotency key. Status returns ID, environment, state, generation and provider ID, never the secret, and reobserves provider ownership before reporting active; a missing or foreign provider resource is unavailable, not a stale active success. Only an exact activation or retry returns the secret with no-store headers. Pending deliveries have no guarantee during deactivation or after it completes.

Core migration `0752` retains the state, keyed request and caller-key digests, provider identity and sealed signing secret. Management owns the separate webhook encryption keyring; its authenticated scope includes organization, project, physical and logical environment, subscription ID and generation. No plaintext secret or customer header enters Core. Six closed private Core methods reserve, finish or abort activation, begin or finish deactivation, and read status. The capacity decision includes existing provider webhooks and in-flight reservations, and a post-create race is fenced before a losing provider webhook is removed. A provider create whose response remains uncertain at 23 hours 55 minutes stays pending rather than crossing the provider's 24-hour idempotency window and risking a duplicate. A sealed active receipt is still recoverable by its exact authorized retry.

This decision changes no incoming provider signature verifier. Hosted synthetic US and EU acceptance covered CRUD delivery, HMAC verification, generation-2 reactivation, lost-reply recovery and capacity-bound replay. A genuinely foreign-principal hosted denial and the separately reported historical missing Production CRUD deliveries remain unproven; the synthetic result does not establish that original delivery. The release required the dedicated Development and Production webhook keys and migration `0752`. Release and acceptance evidence. ## D605 Closed migration failure diagnostics

Status: **Released in 0.1.57; scoped US/EU hosted acceptance passed** (15 November 2026).

<a id="d605"></a>

Decision: when PostgreSQL definitively rejects a customer migration statement and rollback is confirmed, the deployment may retain the canonical file and, together, its one-based statement index and valid five-character SQLSTATE with the closed migration-failure reason. PostgreSQL messages, SQL and parameter values are not public diagnostics. Transport loss, shutdown, an unclassifiable statement outcome and an unconfirmed rollback remain uncertain and enter reconciliation; they are not asserted to be a definite customer SQL error. Admission, ledger and catalog failures can carry their bounded reason and file without inventing a statement index.

Hosted Production acceptance in US and EU exercised a failing migration with SQLSTATE `42P01` at statement 2; operation GET, event stream and project status agreed, and rollback was observed. This establishes that bounded synthetic path, not the cause of an earlier customer report. Release and acceptance evidence.

The operation's current failure row stores that validated metadata separately from the immutable `OperationFailed` event, whose failure remains exactly code and message. Authorized operation GET, event stream and project status re-render the same closed public diagnostic and reject unexpected diagnostic members. The bounded information helps locate a failure without treating provider text or customer SQL as a trusted instruction. ## D612 A failed operation's orphaned registration reservation is superseded after seven days

<a id="d612"></a>

**State:** implemented in source (Core migration 0920, `supersedeCommand` in `registration.ts`); release and live acceptance pending. **Context:** A reservation of an operation that failed and never registered can never become a receipt, because every registration needs the operation's provider mutation claim and a failed operation releases it. Such a reservation still blocked every later registration of the database, so the deploy path refused forever. **Decision:** the reservation commands first delete the pending reservations of failed operations whose claim is gone and whose failure is at least seven days older than the claim's own operation (its `created_at`). The `delete_after_receipt` trigger admits only that deletion (or a deletion of a receipt-backed row); a reservation of an open or succeeded operation never leaves, and no reservation is updated or adopted. The seven-day window is an application rule, not a database clock. **Consequence:** an orphan blocks a registration for up to seven days, then leaves with its registration attempt; the deploy and data-change reauthorization paths both supersede it. A raw SQL delete of a fresh failed reservation is possible for an operator; the application never does it. ## D623 PGCF compute observation ceiling of 24 hours

<a id="d623"></a>

**State:** implemented in source; release pending. **Context:** A PGCF compute job whose status reads keep failing, or whose operation never reaches a terminal state, stayed `running` forever. **Decision:** an accepted job ends `failed` (`DATABASE_COMPUTE_FAILED`) after `COMPUTE_OBSERVATION_CEILING_MS` (24 hours) or at once on a permanent PGCF refusal (a 4xx other than 401, 403, 408 and 429); an operator log line `pgcf_compute_observation_overdue` names a job that is overdue. ## D630 Migration SQL policy applies to the files the ledger has not applied

<a id="d630"></a>

**State:** released in Development and Production from `34279d930e7bad78aadb5077ab76896aea79201f`. The same Sign commit deployed to its existing Dev database with unchanged migration files. Release evidence. **Context:** A hosted Sign deployment failed with `database_migration_failed`, reason `not_admitted`, on a migration file that was already applied and byte-identical to the deployed one. The whole bundle was admitted against the current SQL policy before the database ledger was read: in the deployment Worker, in the PGCF runtime and in the executor. A statement the policy had since started to refuse therefore blocked every later deployment of an unchanged, applied file. **Decision:** the Worker and the PGCF runtime check only the bundle structure, because neither can read the ledger; the executor repeats that check, verifies every digest, and then, in its transaction and under the migrations lock, reads `ohmyhost.schema_migrations`. The ledger must be an exact ordered prefix of the bundle by path and digest (an edited, dropped, reordered or inserted applied file is a `ledger_conflict`). That proven prefix keeps the structural rules (count, ordered unique paths, sizes) but skips statement policy and is never executed again; every pending file is admitted by the unchanged current policy, SQL validation is not relaxed, and a refusal rolls back with `not_admitted` and the pending file's path. `admitMigrationsAfterAppliedPrefix` takes its count only from that proven ledger prefix. **Consequence:** a fresh bundle with refused SQL is no longer rejected before the provider claim and database placement; it fails in the executor with the same diagnostic after the placement and the idempotent role grants, and `ohmyhost init` still rejects it before a build. The change is not a policy change, so it is outside the [D429](delivery-and-operations.md#d429) policy cohort; it ships in the deployment workflow Worker and the PGCF-runtime Neon-management Worker, Development before Production.
