D436 follow-up, 22 October 2026: A cache never decides a result. Turbo keys each build task by its package files, its dependencies' hashes, the root `tsconfig*.json`, the root Node and pnpm engines, its declared inputs and its locked external dependencies; tsc keys each file by content hash. Compared with a cold computation on an 18-core Mac, not on CI: a docs-only edit hit 56 of 56 build tasks in under a second (0 of 56 and 42 s under the old global scopes), and every package's `dist` hash equalled a cold build's (wrangler's timestamped `README.md` aside); with warm build information, a required method added to `ManagedSourceGitPort` broke the same two packages with the same three TS2741 errors as a cold typecheck, including the `database` test that imports the interface by relative path, which a replayed Turbo result would have hidden; the typecheck took 73 s cold and 26-32 s warm. The Turbo entry is stored from `.turbo/cache` under `turbo-v2-<os>-<arch>-<node>-<pnpm>-<hash of the lockfile, the workspace file and turbo.json>-<commit>`; the same key without the commit is the restore prefix, so the newest earlier entry is found and a changed lockfile, `turbo.json`, Node or pnpm starts cold. Turbo never evicts an entry, so the build job removes the entries its own `TURBO_RUN_SUMMARY` does not list before it saves (about 20 MB); the previous setup stored one near-identical entry per job and commit, which left the repository cache at 126 entries and 9.1 of 10 GB. The build information of the 56 packages (7.6 MB, 2.0 MB compressed, relative paths only) is stored under `tsc-v1-<os>-<arch>-<node>-<typescript>-<hash of the lockfile and every tsconfig>-<commit>`. The key covers every `tsconfig` because tsc keeps the cached result of an unchanged file across a change of some options, `target` and `module` among them: with warm build information, a standalone probe on TypeScript 5.9.2 that lowered `target` to ES2017 passed, and a cold typecheck of the same files failed with TS2737. A failed or cancelled job saves nothing, and an exact key that was restored is immutable and is not saved again. Turbo replays only `dist/**` and `public/pages/**`, while four generators rewrite five tracked files during the build (the portal assets, the public-site pricing, site frame and content, and the skill resources); an entry saved by a build that left one of them changed would be replayed by a later commit with identical declared inputs without that rewrite, and the shards' source-identity comparison would pass on the stale file. The build job therefore fails when `git status` is not empty after `pnpm build`, before it prunes and saves; a local replay (a stale generated file committed, then a docs-only commit) passed when the cache held the entry saved by the dirty build and failed when that build saved nothing. The residual risk is a build that reads a repository file nobody declared. The tooling contract pins the declared files, every `../` path in a build script and the static relative imports of the `node` scripts a build runs; it cannot see a read through a computed path, so a complete declaration is a review obligation. ## D517 Core head, train state and resumed Worker releases

<a id="d517"></a>

## D615 GitHub push body bound and buffered memory

<a id="d615"></a>

**State:** implemented in source (commit 7d4d09ef4); release pending; the 2x memory acceptance is recorded by the owner on 15 November 2026. **Context:** A GitHub push that lists many commits and changed paths is larger than the 1 MiB bound that the WorkOS route uses, so it was refused with 413 before any inbox row existed and no deployment started. **Decision:** the GitHub route bounds the authenticated body at 25 MiB; the streaming bound and the HMAC over the full body are unchanged, and the WorkOS route keeps 1 MiB. The owner accepted the buffered memory of that bound: the reader holds the chunks and one joined copy, about 2 x 25 MiB while it reads. **Consequence:** a correctly signed 3 MiB push is accepted (202). Decoding and JSON parsing add transient copies that the 2x figure does not count, and the bound applies per delivery, not to the sum of concurrent large deliveries in one isolate.
