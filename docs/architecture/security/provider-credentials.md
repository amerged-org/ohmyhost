# Provider credential boundaries

## Credential boundaries

Provider-management credentials are isolated in trusted deployables. Ordinary customer clients call the public REST/generated SDK contract; they do not receive management keys. Private service bindings carry explicit product commands and scoped manifests, not general administrator access. Secret storage and provider privilege are separate questions.

Webhook Ingress may temporarily hold one additional expiring verifier for each exact GitHub or WorkOS purpose. It does not gain issuer-management credentials or a generic secret pool. Authentication checks the unchanged raw bytes before one parse and inbox call; the Core's global provider/event identity and raw-body conflict fence remain authoritative. A configured expiry bounds verifier grace, not provider backlog or successful credential retirement. Natural sender evidence, duplicate-byte compatibility and reconciliation remain separate operator gates. [Bounded verifier policy](../auth-and-secrets.md#bounded-webhook-verifier-overlap), A31 task boundaries.

`ORQ_API_KEY` is a Worker secret of `apps/ai-gateway` only. It enters the Worker once through the standalone creation with `--secrets-file` from a 0600 file outside the checkout, or later through a reviewed secret upload, and never through `vars`, a wrangler file, a log, a build or a customer Worker. The gateway forwards it only to the configured orq origin, which must equal `ORQ_ORIGIN`, and its warning lines carry no key. One orq key per environment is recommended, so Development and Production spend stay separate. Creating, rotating or revoking that key needs its own explicit authorization ([D451](../decisions/delivery-and-operations.md#d451), [AI gateway](../services-and-workers.md#ai-gateway)).

The Credit Service holds no provider-management key and no database credential. The PGCF and R2 collectors keep their provider credentials and only return final usage rollups to it; it posts the resulting charges to the Core through `CreditRuntime`. [Credit Service](../services-and-workers.md#credit-service), [profile](../../../scripts/release-private-worker.mjs), [bindings](../../../apps/credit-service/wrangler.production.jsonc).

The code explicitly binds trusted database management to `ProjectDatabaseAdmin`; customer bindings select `ProjectDatabaseService`. [Admin composition](https://github.com/amerged-org/ohmyhost/blob/main/apps/neon-management/wrangler.production.jsonc#L13), [entrypoints](https://github.com/amerged-org/ohmyhost/blob/main/apps/project-database-runtime/src/worker-service.ts#L36). WFP publication receives the current secret manifest privately and returns credential-free evidence. [Secret publication](https://github.com/amerged-org/ohmyhost/blob/main/apps/wfp-management/src/management.ts#L2905). Recovery secrets are injected into a trusted operation-owned Container, not an untrusted customer build. [Recovery boundary](https://github.com/amerged-org/ohmyhost/blob/main/apps/recovery-container/src/worker-main.ts#L119).

Managed-source token values are treated as opaque provider-issued credentials, not inferred from a documented token prefix. The Git remote is pinned to the configured account/namespace/repository, redirects are refused, and preparation/push happens in trusted memory without running customer scripts. Source exports omit `.git`; the later unprivileged build sees only the exact archive. Persistent source and client-consent records keep identifiers, hashes and receipts instead of provider token values. [Source adapter](../../../apps/source-fetcher/src/managed-git.ts), [private staging/Git RPC](../../../apps/source-fetcher/src/managed-git-rpc.ts), [Connect custody](../auth-and-secrets.md#remote-connect-delegation-and-portal-custody).

WorkOS capability probes return only an allowlisted availability/status/count inventory. Their resource-probe surface is labelled read-only, but a configured private AuthKit M2M flow can perform a token-exchange POST; it does not return that token to the caller. Probe client-secret material stays in the private transport's WeakMap-held credential object. This probe contract does not enable M2M customer authority or make FGA the product authorization backend. [Private probe credential](https://github.com/amerged-org/ohmyhost/blob/main/apps/workos-management/src/workos-readonly-transport.ts#L181), [token exchange](https://github.com/amerged-org/ohmyhost/blob/main/apps/workos-management/src/workos-readonly-transport.ts#L437).

The Domain Management OAuth cipher has a bounded version-reader source candidate: the Worker-only
primary writes one version, while the optional `CLOUDFLARE_OAUTH_TOKEN_CIPHER_ADDITIONAL_KEYS_JSON`
secret retains old readers for general/scoped grants, late old writes and protected recovery copies.
No key or map value belongs in source or customer bindings. The active profiles require both custody
bindings and declare the proposed writer version; their activation is separately gated. The existing
private `--secrets-file` release stages new code, new primary and retained readers in the same
qualified version, then activates that exact version. The old serving binary's closed inventory
must not receive the new map in advance. Historical readers survive a writer rollback. [Cipher and callback boundary](../storage-and-domains.md#oauth-token-version-readers-source-candidate).

The bounded Production Domain keyring entrypoint has only its existing provider/Core capabilities
and the OAuth reader map. Full Native composition remains strict; the bounded profile cannot opt
into a Core train, introduce Native grants or retarget the existing six private services. The
same shared implementation preserves the observed original Production wire and identity policy.
[Explicit source boundary](../storage-and-domains.md#bounded-production-domain-keyring).

Native Auth custody is regional and distinct from customer runtime-secret encryption. Its source
candidate labels the primary by the Native writer version and retains explicit old readers for
registry, engine-secret and mail/invitation envelopes. The stable inner engine secret is preserved;
master-derived restore HMAC receipts use bounded exact-text historical lookup. New code and keys
activate atomically without rewriting realms or dropping protected backup readers. No master or
reader map is exposed to customer code. [Native custody](../auth-and-secrets.md#native-custody-version-readers).

Dev and Prod credentials are independent. The repository declares intended service/resource restrictions and validates many exact identities, but this audit does not read live provider token scopes, root access, local credential files or every external key copy. Separate Cloudflare account ownership is not inferred from service names: explicit account/resource configuration is the evidence. Infisical's empty provider package is not current customer-secret custody; AWS and age/X25519 descriptions from earlier baselines are historical, not the active recovery path.

For each credential, operators must retain its actual issuer, consumer, allowed resources/actions, lifetime, rotation/revocation method and recovery requirements. Changing a credential or removing ingress requires the separately authorized operational procedure; documentation review does not authorize rotation or deployment. See [exact customer/key custody](../auth-and-secrets.md).

W25 shared sender custody keeps a single workspace provider resource and immutable original encryption coordinates; attaching a project does not copy, decrypt into its runtime, rotate or relabel the provider key or original DNS grant. A project receives only its own environment gateway key. Deleting/transferring the creator must not orphan surviving resource decryption. New application-proof and workspace-mail DNS grants have separate resource/purpose/revision custody and consent. [Mail ownership](../mail-and-recovery.md#same-domain-shared-sender-contract), [proof flow](../storage-and-domains.md#application-identity-before-mail-gated-deployment). This approved implementation contract does not establish a deployed credential migration.

W26 adds no credential or secret. The egress policy Worker gains one service binding, to the named `StorageEgressEntrypoint` with the static props `{ caller: "wfp-egress-policy" }`, beside its mail binding, and one plain variable for the storage gateway origin; it has no database, R2 or Resend credential and logs no key. The storage gateway keeps its exact five bindings and its R2 credential. The caller marker is a misconfiguration guard, not a credential: only platform-built bindings can reach the entrypoint, and customers hold only the gateway URL, the project and environment IDs and their environment key. [Relay](../services-and-workers.md#customer-gateway-and-outbound-policy), [threat model](threat-model.md), [D437](../decisions/domains-and-mail.md#d437).

W37 adds private Native custody: regional Auth registries encrypt each environment's runtime URI and engine material; PGCF management retains provider/migration/backup authority. Control encrypts customer-owned Google/GitHub client secrets under exact organization/project/environment/provider coordinates, and the private resolver rechecks current authority before and after decryption. Customer Workers receive only deployment-scoped read-only `NativeSessionService` through `OHMYHOST_AUTH`; browsers reach the closed gateway path. Native mail resolves the authorized customer sender privately. [Native policy and custody](../auth-and-secrets.md#customer-application-auth), [provider-secret resolver](../../../apps/control-api/src/native-auth-provider-secrets.ts), [registry](../../../apps/native-auth-runtime/src/registry.ts), [mail boundary](../mail-and-recovery.md#native-auth-mail-and-recovery-candidate). These are in-progress source boundaries; no deployed credential/profile verification, Astra approval or release is implied.

The Growth Access application audience tags are public application identifiers used in JWT validation, not bearer credentials. The secret scan has exact-value, exact-profile exceptions for those two tags only; JWT signature, issuer, audience, expiry and configured operator permissions remain mandatory. See [Cloudflare's application audience validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/) and [Growth](../growth.md).

## Product Preview credential custody

The W41 VM contains customer code and customer-owned environment values, not platform credentials. SourceFetcher retains Git/GitHub credentials; regional Database Workers retain PostgreSQL credentials; Native Auth retains its signing secret. `RuntimeSecretDeliveryPreview` receives only the current preview fence and reads scoped encrypted envelopes through `PreviewSecretAuthorityRuntime`. It injects the existing mail/storage/AI key into private gateway requests outside the guest. The request cannot select an organization, environment, alternate provider origin or authorization key. There is no automatic replay of a possible write after a lost reply.

Capability labels are generated from 256 random bits, encrypted with the existing versioned environment keyring under feature/preview/token-generation AAD, and stored in Core as ciphertext plus lookup hash. Authorized API recovery returns the stable URL; audit/operation hashes, logs and receipts exclude its plaintext. Rotation closes old-generation connections before confirming the new capability. Permanent capabilities do not expire until rotation/deletion; task-only credentials retain a short lifetime and are deactivated on completion. This source boundary is covered by [D608](../decisions/runtime-and-lifecycle.md#d608); actual hosted acceptance requires its release receipt.
