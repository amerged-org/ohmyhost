# Data classification

Classify at the highest applicable level. The table describes current handling requirements and implemented custody; it does not invent a universal provider retention duration or certification.

| Class        | Current examples                                                                                                                                               | Custody and access                                                                          | Logging and deletion                                                                                                                     |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Public       | Published API schema, public Skills, chosen public app content and URLs                                                                                        | Public by the owner's explicit product/publication choice; preserve integrity               | Publish deliberately; retain version evidence separately                                                                                 |
| Internal     | Architecture, capability map, non-secret account/resource IDs, release identifiers                                                                             | Operator and workload scope; an ID is not automatically a credential                        | References may be logged when needed; do not infer unlimited retention                                                                   |
| Confidential | Customer source, private artifacts, project configuration, usage, invoices, feedback, application records                                                      | Concrete tenant authorization, private storage and purpose-limited access                   | Prefer correlation IDs and redacted excerpts; lifecycle/retention follows its subsystem contract                                         |
| Restricted   | Bearer tokens, signing/private keys, database URIs/passwords, provider API keys, secret values, recovery configuration, SQL archives and download capabilities | Worker secrets or specifically encrypted scoped records; access only by the named custodian | Never put values in source, general logs, build inputs or public bundles; expiry/revocation/deletion follows the credential/job contract |

Customer runtime secrets are encrypted in the Core D1 and copied into the exact customer's Cloudflare runtime bindings. Database runtime URIs are encrypted separately in regional Durable Object storage. User API-key values are revealed once; a deliberate local client credential file is local custody, not a server-side reversible token vault. SQL backup passwords are customer-owned, with a separate temporary encrypted job-input envelope. See [custody](../auth-and-secrets.md).

Public client IDs and publishable integration keys must follow their provider contract. Resource IDs, repository selections and domains can disclose topology and therefore remain tenant-scoped even when they cannot authenticate a request. A short-lived provider credential remains Restricted. Base64 encoding is not encryption.

Dev and Prod use independent platform credentials and configuration. Tests/fixtures contain deterministic or explicitly scoped disposable values, not real customer values. Do not introduce a staging environment claim where only Dev/Prod configuration exists. Provider responses, customer feedback, source and SQL are untrusted inputs; they do not become instructions to an operator or another agent.

The append-only audit records preserve actor/scope/operation/result identifiers rather than secret values. The credit log keeps organization and project identifiers, meters, quantities and amounts, never secrets: the Core holds today's rows and the private EU R2 bucket holds each rotated day for 14 days ([Credit Service](../services-and-workers.md#credit-service)). Deletion removes operational credentials and resources after scoped cleanup, while authorized audit history has its own retention obligations. Document any remaining provider backup/retention limitation rather than promising immediate erasure everywhere. Scoped secret storage, secret removal.

Managed source bytes, version history, staged manifests and local snapshot inventories are Confidential and tenant-scoped. Client-grant metadata and public OAuth client IDs are not bearer credentials, but user/client/consent/project associations still disclose private topology. WorkOS Connect access/refresh tokens, Artifacts repo tokens and opaque portal links are Restricted. Handoff records retain link/consent hashes and metadata, not secret values; proof receipts omit credential values. Provider tokens stay in trusted request memory and are excluded from source/build objects. [Remote custody](../auth-and-secrets.md#remote-connect-delegation-and-portal-custody), [managed staging](../storage-and-domains.md#managed-source-staging-and-repository-history). Workers Logs stores the full request URL of each invocation. The Control API's portal handoff `request`, the provider callbacks' `code` and `state` and the browser-login callback therefore reach the logs unless invocation logs are off, so the Control API Wrangler profiles set `observability.logs.invocation_logs` to `false`. The MCP and webhook-ingress profiles (Development and Production) do the same, because their logs carry request URLs as well. That setting is not part of the versioned upload: the live Worker keeps its current setting until a release applies its declared block, and only the two Control API Workers are read back after a release.

W37 Native directory/profile/provider-subject associations are Confidential tenant data. Password hashes, opaque sessions, mailbox/invitation challenges, OAuth state, encrypted provider credentials, Native registry URIs and Auth SQL archives are Restricted. Provider access/refresh/ID tokens are discarded after in-memory identity validation; database constraints also prohibit their persistence. Public management projections and audits omit these values. The Core holds policy/receipt metadata and sealed inputs, while the private Auth database and registry hold their distinct directory/credential material. [Native custody and policy](../auth-and-secrets.md#customer-application-auth), [schema constraints](../../../apps/neon-management/src/native-auth-schema.ts), [archive custody](../mail-and-recovery.md#native-auth-mail-and-recovery-candidate). This classification records the source candidate, not a live retention or logging audit.

Native-bearing encrypted export bytes remain Restricted while an upload outcome is uncertain or its Core retention has not been retired. The permanent export marker contains fixed nonsecret bytes, while its tenant-scoped locator and Core effect/retirement metadata remain Internal/Confidential as applicable. A marker's presence proves that an old create-only upload cannot reintroduce payload; it is never described as literal R2 object absence. [Protected export custody](../mail-and-recovery.md#protected-native-export-settlement-candidate).

Scoped Cloudflare DNS refresh tokens are Restricted. A pair displaced by a re-authorization is kept only until the Domain Management sweep has revoked it and Cloudflare has accepted the revoke, and is then deleted; a failed revoke keeps it for the next sweep ([D476](../decisions/domains-and-mail.md#d476)). Mail webhook signing secrets are Restricted and change by generation, so a rotated secret stops verifying at once ([D477](../decisions/domains-and-mail.md#d477)).

W49 Growth measurement includes pseudonymous event and fact data and restricted attribution snapshots. Its bounded retention, deletion replay suppression and explicit reveal are described in [Growth](../growth.md).

Growth segment tags identify accounts or organizations; segment audit rows retain the operator and a subject digest, with a 180-day expiry. Coarse daily cohort counts have a minimum of five, but that threshold alone is not proof of anonymization. See [Growth](../growth.md).

Native Auth user deletion erases the address from `native_admin_receipt` and `native_mail_outbox`. Each receipt for the user keeps its request digest and an empty `user.email`; a replay of its create-invite, resend, suspend, reactivate or revoke-sessions request answers `resource_not_found` (404) because the user is gone, while the delete's own replay still answers. Each invitation outbox row keeps its delivery record with its sealed payload emptied, so the delivery proof still answers. The pseudonymous user ID stays on audit and outbox rows. Two residuals remain open: `native_password_receipt` sign-up bodies still carry the address because they have no user reference, and an invitation receipt's unkeyed request digest still covers the address for replay conflict detection.
