# Credit Service: what the Core provides

The Credit Service consumes the Core only through `CreditRuntimePort` (`src/port.ts`), which mirrors the W33 contract's `CreditRuntime` (with the rules of `postUsage`, `deleteLogThrough` and `readLogsToday` under "Semantics" that refine it), plus the three reads below. All of it is implemented by `apps/control-store/src/catalog/credit/` (`runtime.ts`, `attribution.ts`). Every timestamp crossing the binding is a `Date.prototype.toISOString()` string (`2026-10-30T09:00:00.000Z`, millisecond precision, `Z`); the service compares them as strings and as dates, so the Core must store and return that exact form.

## Additional Core methods

The contract's `CreditRuntime` cannot attribute PGCF databases, R2 buckets or lifetime resources to an organization, project and environment. Add these three methods to the `CreditRuntime` entrypoint (read only, no writes). They are declared as `CreditRuntimeAdditions` in `src/port.ts` and implemented by the in-memory port of the tests.

```ts
resolvePgcfDatabases(i: { databaseIds: string[]; at: string /* hour start */ }):
  Promise<{ databaseId: string; organizationId: string; projectId: string; environmentId: string }[]>;
```

Customer-owned PGCF databases (at most 100 ids per call, `at` an hour start) that were serving and billable during the hour starting at `at`. A database that is platform-owned (`pgcf_platform_database_activations`), unknown, not yet billable, or whose hour is split across serving intervals with different owners is omitted: the service then bills nothing for it and counts it as `databases_unowned`. A database is billable from the first full hour after its serving interval started (`billable_from`); an interval that stopped inside an hour still bills that hour; databases are matched by `database_id` alone. `environmentId` is the logical environment when exactly one is assigned to the database in that hour, otherwise the physical environment id (the logical environments are those whose latest assignment pointed at the database's data environment both at the start and at the last microsecond of the hour; the old `pgcf_usage_hours` rules, minus the billing-epoch and activation machinery).

```ts
listR2Buckets(i: { day: string /* UTC midnight */; after: string | null; limit: number }):
  Promise<{ buckets: { bucketName: string; jurisdiction: "eu" | "us"; organizationId: string;
                       projectId: string; environmentId: string }[];
            next: string | null }>;
```

Every customer bucket (`project_r2_bucket_receipts`) that existed during the UTC day starting at `day` (created before the day closed, project not deleted before the day began), with the owner at the end of that day (the organization of the project's open `billing_epochs` row; the bucket's environment is the receipt's environment), ordered by `jurisdiction, bucketName`, paginated by an opaque `after`/`next` cursor (`limit` is 200; the Core accepts up to 1000). The service passes the bucket names to `R2ManagementService.collectUsage`, which reads the provider's class A/B counts and the confirmed storage peak (`R2ManagementRuntime.confirmedStorage`), so this list is also the complete set of billed buckets.

```ts
readResources(i: { day: string /* UTC midnight */; after: string | null; limit: number }):
  Promise<{ rows: { organizationId: string; projectId: string; environmentId: string;
                    scripts: number; hostnames: number }[];
            next: string | null }>;
```

Per organization, project and environment: the number of WFP scripts (`wfp.script`: `wfp_candidate_receipts` staged before the day closed and without a `wfp_candidate_cleanup_receipts` row before then) and linked custom hostnames (`domain.custom_hostname`: `paid_project_domains` with a custom hostname receipt, provisioned and not deleted by then, counted in the project's `prod` environment) that are active at the end of the UTC day starting at `day`. The owner is the project's owner at the end of that day; a project deleted before then has none. Rows with both counts zero may be omitted. Ordered by `organizationId, projectId, environmentId`, paginated like the bucket list (`limit` is 500; the Core accepts up to 1000). No waiver machinery: the service multiplies the counts by 86 400 seconds and prices them with the `resources-*` card (`script_second`, `hostname_second`, 744 hour month).

## Semantics the service relies on in the contract methods

- `postUsage`: idempotent on `usage:<source>:<org>:<window>` for a whole window and for part 0 of a split one, and on `usage:<source>:<org>:<window>:p<part>` for a part from 1 to 255 (`posted: false` for a repeat, nothing else changes). A whole window sends neither `part` nor `split` (the posting of a Core before parts); a split window sends `split: true` and `part` on every posting, and a part above 0 without `split` is refused. A posting carries at most 2000 lines. A window is booked in one layout: the first posting decides it (`split: true` in the stored detail), and a posting of the other layout books nothing and answers `{ posted: false, balanceMicros, layout: "whole" | "split" }`, the booked layout. The check is a guard inside the booking batch (the batch fails on `precondition_changed` when a booked row of the window has the other layout), so overlapping invocations cannot book both; the same batch deletes the failure kept for the key and those kept for the other layout of the window. Booking a key, now or before, or answering a layout refusal, removes the failure kept for that key. `window` is the ISO start of the hour (`wfp`, `pgcf`) or of the UTC day (`r2`, `resources`). **The row's `at` is the START of the window** (the time the usage happened, so the report and the day rotation see it on the right day); other kinds are filed at the Core's clock. `seq` is therefore the order of posting and NOT the order of `at`: the first window of today is posted (01:27) before the last window of yesterday (the PGCF rollup is final only two hours after the hour, 02:27). The service never posts an empty `lines` array. `chargeMicros` is a safe integer; the service computed it from `readRates` with `evaluateRateCard` (rounding up once per line).
- `recordUsageFailure({ organizationId, source, window, part?, split?, lines, reason, limit, immediate })`: keeps a posting that could not be booked in `usage_post_failure` under its log key, with the lines and layout of the latest attempt, and returns `{ attempts, dead }`. `attempts` counts the failures; it is raised to `limit` when repeating cannot help (`immediate`, or the Core finds the kept lines unbookable itself: the service cannot tell, because a validation error reaches it as a plain `Error`) and when the organization already has a posting for the source with `attempts >= limit`, and `dead` is `attempts >= limit`. A posting whose key is booked, or whose layout is not the booked one, is not kept: the answer is `{ attempts: 0, dead: false, settled: "booked" | "superseded" }`. The lines are stored as sent and not validated, because a posting may fail because of its lines. The service holds the cursor of the window while a posting is not dead and lets it pass when every failed posting is dead.
- `replayUsageFailures({ minAttempts, limit })`: books the kept postings with `attempts >= minAttempts` and lines, oldest failure first, each under its original key and layout and filed at the Core's clock (the day of its window may be rotated already), removes the row of a posting that is booked, and counts one more attempt for one that still fails, which then goes to the back and waits 30 minutes, doubling to a day. It books at most `limit` postings, more while many are due (a fifth of them, at most 100), and returns `{ replayed, remaining }` with `remaining` every kept posting at or beyond `minAttempts`, also those without lines or waiting. The service calls it with 4 and 20 in every pass and fails the invocation while `remaining` is above 0. The kept rows are written and settled on the raw Core route, so a fenced bucket does not stop them and a replay after the fence is lifted books the posting. A kept posting for an organization without an account is answered without a booking: its row stays, counts in `remaining` and makes the pass report `incomplete:replay`, for an operator.
- `readCursor` / `advanceCursor`: `through` of `wfp` and `pgcf` is hour aligned, of `r2` and `resources` UTC-midnight aligned. `advanceCursor` never moves back and accepts the value it already holds. The service does nothing for a source whose cursor does not exist: the operator inserts the four rows at cutover, and a misaligned value fails the pass loudly.
- `resolveScripts`: at most 100 names per call, unknown scripts omitted, only names matching `p-<26>-(dev|prod)-<26>` are sent.
- `readRates({ at })`: the published cards in force at `at` whose meters are activated, as `{ rateCardId, rates }`. `rates` is the stored card row list (`{ meter, unit, units_per_charge, provider_cost_micros, credit_micros }`, decimal strings), or the platform `Rate` shape (`unitsPerCharge`, `creditsPerCharge`, `providerCostPerCharge`; `bigint`, decimal string or safe integer). Every published card rounds up with no minimum. A meter that no returned card prices is not billed and is counted as `unpriced:<meter>`; a meter on two returned cards is an error.
- `readLogPage({ beforeAt, afterSeq, limit })`: rows with `at < beforeAt` and `seq > afterSeq`, ascending by `seq`, at most `limit` (the service asks for 500); `lastSeq` is the `seq` of the last returned row, or `afterSeq` when none.
- `deleteLogThrough({ seq, beforeAt })`: deletes the rows with `seq <= seq` AND `at < beforeAt` (both are required). The service calls it only after every shard object and the manifest were read back, with `seq` = the highest `seq` it archived and `beforeAt` = today 00:00Z, the boundary it read the rows by. The `at` bound keeps a window of today that was posted before a late window of yesterday: it has the lower `seq` but must not be deleted. The service reports `credit_log_deleted:<deleted>/<archived>` as a problem when the counts differ.
- `listStopBudgetProjects()`: at most 50 `{ organizationId, projectId }` rows, in no particular order, of the projects whose `stop` budget is reached in the current month (use of the month plus open reservations at least the budget; a `continue` budget, a missing budget, a past month's use and an inactive project are left out). Read only; it is the rule of `runtimeDecision` in SQL, and a Core test checks both against each other.
- `cursorsThrough`: every `usage_cursor` row. Rotation waits until each `through` is at or after today 00:00Z.
- `readLogsToday({ organizationId })`: every row of the organization that is still in the Core log (today's rows and any older row that has not been rotated yet), oldest posting first, with no day filter despite the name. The usage report merges these with the rotated shards by `key`.

## Collectors (already changed in this lane)

- `NeonUsageService.collectUsage({ from, to })` (`apps/neon-management/src/pgcf-rollups.ts`): final hourly PGCF memory rollups of an hour-aligned window of at most 24 hours that ended at least 2 hours ago, plus `pending`: every `{ databaseId, hourStart }` row the provider has not finalized yet (at most 24 000; more fail the read). A retired database can stay pending forever, so the service passes an hour only when no pending row of that hour resolves through `resolvePgcfDatabases` (asked per hour, 100 ids per call, oldest hour first); a pending row that does not resolve for its hour would not be billed even when final and is counted as `pending_ignored`.
- `NeonUsageService.stopSchedules({ organizationId, projectId })` (`apps/neon-management/src/pgcf-stop-schedules.ts`): disables every enabled schedule of the application's runtime role in the project's dev and prod databases and returns `{ stopped }`. Idempotent; a schedule already disabled is untouched; the first failure throws and the next pass resumes.
- `R2ManagementService.collectUsage({ day, buckets })` (`apps/r2-management/src/usage.ts`): final daily usage of at most 100 named buckets for a UTC day that ended at least 1 hour ago.

Both throw on any failure; neither writes to the Core. The Core methods they used before (`PgcfCollectionRuntime`, `claimCollection`, `recordConsumption`, `reserveRequest`, `deferRequests`) are no longer called.
